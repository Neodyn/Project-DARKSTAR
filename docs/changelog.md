# Changelog

All notable changes to this project are documented here. Format loosely follows [Keep a Changelog](https://keepachangelog.com/); this project doesn't yet use formal version tags, so entries are grouped by feature area in the order they were introduced.

## [Unreleased]

### Added
- Config file (`config.json`) auto-created with default values on first run; the bot exits after creating it so values can be reviewed before starting.
- Google Gemini integration for combined speech-to-text and reply generation in a single API call (conserves free-tier quota), with configurable retry/backoff (`GeminiMaxRetries`, `GeminiRetryDelayMs`) and an optional fallback model (`GeminiFallbackModel`).
- Vosk offline wake-word detection (no cloud account needed) as the sole hotword engine.
- Fixed-phrase system (`phrases.json`): known question/answer pairs answered directly, with a configurable fallback response and a `RestrictToKnownPhrases` toggle.
- Vocabulary hints (`vocabulary.json`) passed to Gemini to improve transcription accuracy for non-standard-English terms.
- Compact, leveled, colored console logging with full detail always written to timestamped files under `logs/`, plus a global `LoggingEnabled` kill switch and a `DebugLogging` verbosity toggle.
- Config and phrase file syntax/value validation, with warnings written to the log rather than blocking startup.
- Automatic schema-merge: new config fields introduced by an update are added to existing `config.json` files with default values, without touching existing settings.
- Automatic timestamped backups of `config.json`/`phrases.json`/`vocabulary.json` to a `Backup/` subfolder before any automatic edit.
- Windows Service hosting support, using the same executable as the console app (via Generic Host / `Microsoft.Extensions.Hosting.WindowsServices`).
- Optional Discord webhook notifications for bot start/stop and SRS connection loss/recovery, gated behind a `DiscordEnabled` flag (default `false`) so the integration is entirely opt-in.
- Multi-radio support (`Radios` list): multiple frequencies monitored simultaneously, each with independent hotword detection, recording state, and reply channel.
- Coalition awareness: requester's coalition is looked up from the SRS client list; `RestrictToOwnCoalition` can make the bot ignore requests from the opposing coalition entirely.
- Per-radio custom wake word and callsign (`Radios[].Keyword` / `Radios[].Callsign`), falling back to the global `VoskKeyword`/`BotCallsign` when unset.
- Blazor Hybrid (WPF + WebView2) GUI configuration editor (`Darkstar.Gui`) covering Connection, Radios, Speech, Phrases, Vocabulary, Discord, and Logging settings, sharing `Darkstar.Core` with the bot service so both always read/write the same config files.
- Automatic shared-config-folder detection so the GUI and the bot service resolve to the same `config.json`/`phrases.json`/`vocabulary.json` by default.
- Player-name callsign parsing: pilots named `CALLSIGN 1-1 | PlayerName` in DCS are addressed as `CALLSIGN 1-1` in replies, with the separator configurable via `PlayerNameCallsignSeparator`.
- TTS-friendly callsign pronunciation: hyphens in spoken callsigns are replaced with spaces so "1-1" is read as "one one" rather than being misread as "eleven" or spoken with an audible pause.
- Inno Setup Windows installer bundling the bot, the GUI, and a Vosk model, with optional Windows Service registration and automatic `VoskModelPath` configuration.
- Installer now also installs every runtime dependency the bot and GUI need on a bare Windows machine: the .NET 8 Desktop Runtime (covering both components), the Visual C++ Redistributable (needed by Vosk's native `libvosk.dll`), and the WebView2 Runtime (needed by the GUI) — each skip-if-already-installed. Both projects switched from self-contained to framework-dependent publishing accordingly, keeping the installer smaller.
- DCS-gRPC groundwork: NuGet bindings (`RurouniJones.Dcs.Grpc`), a `DcsGrpcTester` connectivity check, and a GUI test panel, as the foundation for future real mission-data features (bogey dope, picture, bullseye calls).
- Slim installer variant: `build-installer.ps1 -Slim` (alias of `-SkipVoskModel`) passes `/DNoVoskModel` to Inno Setup, which drops the speech model, its component and the pre-filled `VoskModelPath` from the installer - a few MB instead of up to ~2 GB - and names the result `DARKSTAR-Setup-<version>-slim.exe` so both variants can sit side by side.
- `build-installer.ps1`: builds the whole distributable installer with one command - checks the build machine's prerequisites (.NET 8 SDK, Inno Setup, offering a winget install for the latter), publishes bot and GUI, downloads the three dependency installers and a Vosk model of the chosen size, and compiles `installer\Setup.iss`. Re-runnable, with `-DryRun`, `-Clean`, `-SkipVoskModel`, `-SkipDependencyDownload` and a `-Version` that is now passed through into the installer and its file name.
- Selectable contact source for the tactical replies (`DcsIntelContactSource`): `AwacsThenMissionData` (the previous behaviour), `AwacsOnly` - god's eye switched off entirely, so an empty detection table is honestly reported as a clean picture - or `MissionDataOnly`. In `AwacsOnly`, a failed sensor call or a missing unit name answers "no tactical data" instead of implying an empty sky, and a threat circle skips that sweep rather than suggesting the airspace is clear.
- Threat circle: a pilot can arm a standing watch by radio ("Overlord, threat circle forty miles") and the bot then keeps checking a circle of that radius around the pilot's own aircraft - it moves with them - warning them on the same frequency as soon as a hostile aircraft or helicopter enters it. The radius is understood as digits or words; each contact is announced once per circle; warnings are capped per sweep so a whole package can't monopolize the frequency, and they hold briefly while the pilot is transmitting. A circle ends by voice command, after a configurable time limit, or when the pilot leaves the mission.
- Clearer speech pacing for tactical replies (`DcsIntelSlowSpeech`, on by default): bearings get a comma between their digits so TTS pauses briefly instead of running "zeroninerzero" together, and ranges, altitudes and counts are spelled out as words ("thirty five miles" rather than a rattled-off "35").
- Aircraft/helicopter type announcement in tactical replies is now on by default (`DcsIntelSayContactType`), covers picture and threat calls as well as bogey dope, strips DCS variant suffixes before speaking (`F-16C_50` → `F-16C`), and reports a group flying several types as "mixed, lead &lt;type&gt;".
- `ExternalAudioExtraArgs`: free-form extra command-line arguments appended to every `DCS-SR-ExternalAudio.exe` call, for options that depend on the installed SRS version (such as a speaking-rate flag).
- Windows Service management in the GUI (new CH9 panel, backed by `WindowsServiceManager` in `Darkstar.Core`): install the bot as a service with optional delayed auto-start, start/stop it, and remove it again — the removal stops the service and waits for it to actually reach "Stopped" before deleting, so no ghost entry is left behind. Shows the live state and the executable the service is really registered to run, detects an installation made under the installer's service name, and asks for elevation per operation (UAC) instead of requiring the editor itself to run as administrator. Implemented via PowerShell rather than by parsing `sc.exe` output, which is localized and unparseable on non-English Windows.
- Tactical replies from live mission data (`DcsIntelService` in `Darkstar.Core`, configured on the GUI's DCS-gRPC panel): the bot answers "bogey dope", "picture" and "threat check" from the running mission instead of from `phrases.json`/Gemini. Contacts come from the sensors of a configured AWACS unit (`ControllerService.GetDetectedTargets`) and fall back to plain mission data when no unit is configured, the unit is player-flown (DCS only fills AI detection tables), or the call fails. Bearings are magnetic and read digit by digit for TTS, bogey dope gives BRAA with aspect (hot/flanking/beaming/cold) from the requesting pilot's own aircraft — located by matching their SRS name against the DCS player names — and falls back to the bullseye format when that pilot can't be identified. Includes range/group limits, configurable trigger phrases, and a GUI test button that shows the exact reply without transmitting.
- Optional "message received, standby" acknowledgement (`AckEnabled` / `AckAfterSeconds` / `AckMessage`, editable in the GUI's Speech panel): if transcription and reply generation take longer than the configured number of seconds — counted from the wake word — the bot transmits a short holding message so the pilot knows the call was picked up. Sent per radio with that radio's own callsign, supports `{pilot}` / `{callsign}` placeholders, is skipped entirely when the real reply is ready in time, and never talks over a pilot who is still transmitting (transmissions per radio are serialized).
- DCS-gRPC mission data explorer in the GUI (CH8, backed by `DcsGrpcExplorer` in `Darkstar.Core`): a strictly read-only browser for what a running mission exposes - 38 queries across mission, time, world, coalition, players/server, group/unit, environment and live event/unit streams, shown as raw JSON. Includes a one-click mission snapshot, autocomplete of unit/group names discovered in earlier results, "take position from unit" for weather/declination queries, time-limited live stream recording, and copy/save-to-file (`grpc-dumps/`).
- SRS installation detection (`SrsPaths` in `Darkstar.Core`): the installer now seeds `ExternalAudioExePath` in the initial `config.json` with this machine's real `DCS-SR-ExternalAudio.exe`, found via SRS's own uninstall entry in the registry or, failing that, by probing the known install layouts under both `Program Files` folders, per-user locations and every fixed drive. The config editor's CH1 Connection panel gained a **Detect SRS installation** button that does the same at runtime (and also resolves a folder typed into the field to the executable inside it), and startup validation now names the path it found when the configured one doesn't exist. The installer's `WriteInitialConfig` runs for every variant now, so the slim installer seeds the SRS path too.
- Installer upgrades an existing installation in place: a stable `AppId` plus the version written to (and read back from) the uninstall registry entry let it tell an update from a reinstall from a downgrade, it reuses the previous install folder and component/task choices, states on the "Ready to Install" page which of the three it is, and asks for confirmation before installing an older version over a newer one. The Windows Service is stopped in `PrepareToInstall` and started again afterwards - without that, the update fails on a locked `Darkstar.exe`, since a running service holds its own executable open - and a service registration pointing at an old path is removed and recreated rather than left stale. `CloseApplications` handles a config editor that happens to be open. `build-installer.ps1 -Version` now validates the version and derives the four-part `VersionInfoVersion` for the Setup.exe's file properties.
- Readable startup failures instead of runtime crash dumps: `BotService.ExecuteAsync` wraps the whole startup, logs what went wrong as a sentence with concrete next steps, and stops the host with a meaningful exit code (2 = configuration, 3 = unexpected); `Program.cs` additionally logs unhandled and unobserved-task exceptions to the log file, which is the only place a Windows Service leaves any trace at all.
- Proper anti-alias filtering before the 48 kHz → 16 kHz reduction that feeds Vosk (`AudioFrontEnd` in `Darkstar.Core`), which is the audio path wake word detection depends on. The previous code averaged three neighbouring samples and dropped two, leaving content above 8 kHz only 5–22 dB down as it folded back into the speech range — 10 kHz landing on 6 kHz, 12 kHz on 4 kHz, right where consonants are told apart. A 161-tap windowed-sinc low-pass puts those fold-over products 60–79 dB down instead (measured against test tones, not estimated). The filter also carries its delay line across the 20 ms frame boundaries, which the old stateless version could not, and no longer loses up to two samples per frame on chunk lengths that aren't a multiple of three. Selectable via `HotwordAudioFilter` (`LowPass` default, `Average` for comparison) on CH3 Speech.
- `Darkstar.exe --test-hotword <file-or-folder>`: runs recorded audio through the real detector in the same 20 ms frames the live path uses and reports hits, misses and what Vosk actually transcribed. `--compare` runs both audio paths side by side and says which did better on that material; `--keyword`/`--model`/`--filter` try alternatives without touching `config.json`. Connects to nothing, so it is safe to run while the service is live.
- `SaveRecordings`: writes every transmission to `recordings\` as a WAV tagged `_hit_` or `_missed_` — including the transmissions where the wake word did *not* fire, which previously left no trace anywhere and are exactly the cases worth studying. Together with `--test-hotword` this turns "did that change help?" into a number. Off by default.
- `HotwordAutoGain`: optional evening-out of how loud different pilots arrive, deliberately timid (amplify only, capped at +16 dB, never adapting on near-silence) and off by default, because an eager automatic gain lifts noise into speech range and invents wake words. Never affects the audio that is transcribed or saved.
- `WavUtils.ReadPcm16` / `ToMono`: WAV reading that walks the chunk list instead of assuming a 44-byte header, so recordings made in Audacity or by SRS itself can be fed to `--test-hotword`; non-PCM and non-16-bit files are refused with a message that says why.
- `AppConfig.LoadReadOnly`: reads config.json without creating it, merging fields, logging or backing anything up, for tools that only want to look at the settings.
- Tolerant pilot-name matching (`PilotNames` in `Darkstar.Core`), which decides whether a tactical reply can use BRAA from the pilot's own aircraft or has to fall back to bullseye. The SRS player name and the DCS player name are typed in different places and rarely agree character for character, and the previous exact comparison failed on all of the usual differences: squadron tags (`[ISAF] Mobius 1-1`), flight numbers written `11` instead of `1-1`, and different spacing or capitalisation. Names are now reduced to a canonical key for comparison, with the rules tried strictest first (exact, then canonical full name / handle / callsign, then a narrow unique-substring rule) and each applied across all units before the next, so a weak rule can never beat a strong one. The substring rule deliberately ignores the unit's callsign field, because that holds the *flight's* callsign shared by every aircraft in it - matching partially there would hand a wingman's BRAA call to the flight lead, which a test now guards against. Ambiguity is refused rather than guessed. Whichever rule matched, or why none did, is written to the log, since the bullseye fallback is silent on the radio and previously left no trace.
- Squadron tags are stripped from spoken callsigns, and flight numbers are spoken digit by digit: "Spare 15" is read as "Spare one five" rather than "Spare fifteen", and `[ISAF] Mobius 1` no longer has its brackets read out. Threat circles are keyed by the canonical name too, so a pilot who rejoins with their tag written differently can still cancel the circle they set up.
- "Runway in use" and ATIS answered from the running mission (`DcsAirfieldService` in `Darkstar.Core`, off by default via `DcsAirfieldEnabled`): live wind, temperature and pressure from `AtmosphereService`, and the runway end with the most headwind. A pilot can name the airfield or leave it out, in which case the one nearest their aircraft is used. Designators are the magnetic heading rounded to ten (0 becoming 36), preferring DCS's own name for the strip when it agrees to within one so the call matches the kneeboard, `L`/`R` included. Exact ties are broken by the smaller crosswind and then the longer runway, so the answer doesn't depend on the order DCS listed the strips in. Units are converted from what DCS actually hands over - Kelvin, Pascals, metres per second, radians - and the altimeter setting is read in hectopascals, inches or both (`DcsAirfieldPressureUnit`).
- Runway headings are read through `CustomService.Eval`, because DCS-gRPC's `Airbase` message carries no runway data and `Airbase.getRunways()` is reachable no other way. Since `Eval` runs arbitrary Lua, the snippet is a compile-time constant that asks for *all* airfields at once so no name has to be interpolated, it only reads, and it runs once per DCS session; tests assert those properties. `Eval` is disabled on DCS-gRPC servers by default, so a refusal is reported once with the exact setting to change (`evalEnabled = true`) and the weather part keeps working with the runway reported as unknown.
- `DcsIntelService.SpeakDigit`: one shared digit vocabulary for every number read digit by digit, so the aviation "niner" that bearings already used now applies to wind, pressure and temperature as well. Temperature is read digit by digit ("temperature one five") rather than as a word ("fifteen"), which is how an ATIS sounds.
- The airfield a "runway in use"/ATIS request is about is now decided by the pilot's own position first, and only then by a name in the transcript. Airfield names are the weakest link in the feature - "Mineralnye Vody", "Kobuleti" and "Batumi" are exactly what speech recognition gets wrong, and a mis-transcription that happens to match a different airfield produced a confidently wrong answer. Within `DcsAirfieldAtFieldNm` (5 NM) of a field the position wins outright, so *"Overlord, active runway for Punch 1-1"* works from the ramp with no airfield spoken at all; deliberately naming a different field still works and the log notes the discrepancy. Beyond `DcsAirfieldMaxDistanceNm` (60 NM) with nothing named, the bot asks instead of reporting a field hundreds of miles away as though the pilot were there. Every reply names the airfield it used and the log says how it was chosen.
- A pilot saying their own callsign now identifies them (`PilotNames.FindMatchInTranscript`), which is a second, independent route when their SRS name and their DCS name don't line up - the usual reason a BRAA call silently becomes a bullseye call. Spoken digits are converted back to figures first (`NormalizeSpokenNumbers`, including "niner"/"tree"/"fife"), so "for Punch one one" and "for Punch 1-1" both reach the unit DCS calls `Punch 1-1`; keys must be at least five characters and match exactly one pilot, so two pilots named in one transmission is refused rather than guessed at. The tactical replies use the same lookup. An airfield name that only matches because it is part of the requesting pilot's own callsign is no longer read as naming an airfield.
- Per-radio roles, so the bot's jobs can be split across frequencies the way a real radio plan does - the AWACS on one, the tower on another. `Radios[].AnswerTacticalRequests` and `Radios[].AnswerAirfieldRequests` are three-way (`null` follows the global switch, which is what every existing configuration keeps doing; `true`/`false` decide for that radio alone), and the global switches remain the master so a radio can narrow what the bot does but never widen it. The startup log states each radio's job, the config editor shows three Default/On/Off buttons per radio with the resulting role spelled out underneath, and validation warns when a globally enabled feature is switched off on every radio.
- A request that lands on the wrong frequency is handed off rather than refused: "Contact Overlord on two five one decimal zero" (`WrongChannelReply`, with `{callsign}` and `{frequency}` placeholders; the frequency is read digit by digit). Only when exactly one other radio serves the request - with two towers configured there is no single right answer, so none is given and the transmission falls through to `phrases.json` as before.
- `setup-dev-environment.ps1`: a PowerShell script that checks/installs the .NET 8 SDK, required Visual Studio workloads, the WebView2 Runtime, and a Vosk model, then does a trial restore/build — including a project-structure check that catches misplaced `.csproj` files before Visual Studio does.
- **The test suite is in the repository.** `Darkstar.Tests` is a fourth project in the solution: 682 assertions, one command (`dotnet run --project Darkstar.Tests`), a readable transcript and exit code 0 when everything held. It needs no SRS server, no DCS, no Gemini key and no speech model - a test that only runs with a mission loaded is a test nobody runs. Until now these lived outside the repository, which meant nobody but their author could run them or check the numbers they produced; that was the largest single gap in the project. No test framework on purpose: the assertions are about spoken sentences, arithmetic and whether the code still matches its own comments, none of which needs xUnit, and a dependency-free test project still builds in five years. `Darkstar.Core` grants it `InternalsVisibleTo`, so the helpers under test stay `internal` rather than being made public purely to be reachable.
- GitHub Actions (`.github/workflows/build.yml`): builds the solution in Release and runs the suite on every push and pull request, on `windows-latest` because `Darkstar.Gui` is WPF and a green tick on Linux would never have covered it. A second job publishes the bot exactly as the installer does and fails if the output contains anything but the file types a running bot needs - which catches a NuGet package quietly dropping localized resource folders or XML documentation into what gets installed on somebody's machine.
- `WavUtils` moved from the bot into `Darkstar.Core`. It is pure PCM/WAV format handling with no console, audio-device or UI dependency, which is what this project means by shared - and the tests build the WAV files they feed through the audio path from it.
- Rate limiting per pilot (`RateLimiter` in `Darkstar.Core`; `RateLimitMaxRequests` 6, `RateLimitWindowSeconds` 120, `RateLimitReply`). Every transmission costs a Gemini call and occupies the frequency while the reply is spoken, so one pilot repeating the wake word - bored, annoyed at being misheard, or with a stuck transmit key feeding cockpit noise - could exhaust the quota for everybody and block the channel at the same time, and neither failure looked like the pilot who caused it. Checked after the coalition check and before the Gemini call, so the request is refused before it costs anything. Three decisions in there are failure modes avoided rather than features: a **sliding window** rather than a cooldown, so a pilot asking three things in quick succession and then flying for ten minutes is never held up; **refused transmissions are not counted**, because counting them would move the window forward on every retry and a limit that turns into a ban is not what was configured; and the refusal is **spoken once and then silent**, because repeating it would occupy exactly the frequency being protected - both cases logged, so a pilot complaining they were ignored leaves a trace. Pilots with no recent traffic are forgotten from the watchdog loop.
- Documentation checks in the test suite, because documentation drifts silently: a setting added to `AppConfig` works perfectly and is simply never written down, and nothing notices for months. The suite now reflects over `AppConfig` and `RadioConfig` and fails when any of the 106 settings is missing from `manual-en.md`, `manual-de.md` or `configuration.md`; it does the same for the nine `--test-hotword` options, for the source-file map in `contributing.md`, and for every internal cross-reference across all nine documents. That last one immediately found a dead link: a reference to the German chapter 8.4 used the English heading's slug, which looks right and never resolves.
- `contributing.md` gained a real source-file map - one line per file across the bot and `Darkstar.Core`, which had grown to 39 files while the document still named a handful - plus the conventions that are not obvious from reading the code: trigger phrases go through `TriggerMatcher`, no trigger phrase belongs in the default vocabulary, nothing user-supplied is interpolated into the runway Lua, decision logic goes in a pure function so it can be tested at all, and a capability that reveals information needs a reason to be on.
- Filled the remaining documentation gaps the new checks turned up: `DcsAirfieldUnknownReply` and `DcsAirfieldUnavailableReply` were only in `configuration.md`, the `--autogain` and `--variants` options were in neither manual, the channel overviews in chapter 6 still described the editor from several features ago, and chapter 8.3 did not mention that switching the tactical replies on is also what brings in the alpha check and the friendly-position card.
- Friendly positions: "Overlord, Punch 1-1, where is Springfield 2-1?" answers where another human player on the caller's own side is, as a BRAA from the caller's aircraft or from the bullseye when that can't be found, with the friendly's own heading because where they are is only half of a rejoin. Aspect is deliberately never given - it describes a contact closing on you, which is meaningless about a wingman. **Off by default**, and assignable per radio as a third role alongside tactical and airfield, because a bot that reads out any player's position on request changes how a PvP server plays and that is the owner's decision rather than a default to hand them.
  - The target is found by POSITION in the sentence rather than by scanning it for names. Such a request names two pilots, and `PilotNames` refuses to choose when more than one is named - the safeguard that caught a wingman being reported as their flight lead. Rather than loosening it, `TriggerMatcher.FindMatchWithTail` returns what follows the trigger and only that is searched, which has exactly one answer. The cost is that the name must come after the phrase; pronouns are recognised as naming nobody, so "where is he?" asks which aircraft instead of reporting no contact on "he".
  - Human players only (`CoalitionService.GetPlayerUnits`). AI units are never pulled in: a candidate list of every AI on the coalition makes misidentification likely, and on this particular request that means confidently telling somebody the wrong position.
  - A caller whose coalition is unknown is refused outright, before any player is looked up. Everywhere else an unknown sender coalition falls back to the bot's own side, which is harmless when the answer concerns the enemy - here it would let somebody in a spectator slot ask where the bot's side is.
  - Answered before the hostile contact query, like the alpha check, so it still works when the sensor source is unusable. A caller asking about themselves gets an alpha check rather than "bearing 000, 0 miles".
- Wake-word variants, for crews that are not native English speakers (`VoskKeywordVariants`, `Radios[].KeywordVariants`, and `HotwordVariants` in `Darkstar.Core`). The hotword runs through a small English model, so on a German-speaking server "Overlord" arrives as "over lord", "oberlord" or worse - and the first of those already failed the `\bOverlord\b` match on the space alone, so the bot stayed silent with nothing anywhere to say why. A radio now accepts a set of spellings rather than one, still matched as whole words, with runs of whitespace inside a variant matching any whitespace. Variants follow the word and not the radio: a radio using the global wake word inherits the global variants, a radio with its own `Keyword` starts from an empty list, because otherwise a tanker on "Texaco" would quietly begin answering to a variant meant for the AWACS. The startup log names every accepted spelling, since they are the one thing that can make a radio react to something that is not its wake word. This is not model training, which would be a Kaldi run with hours of labelled audio; it accepts what the existing model already produces.
- `Darkstar.exe --test-hotword recordings --suggest-variants`: works the variant list out of real recordings instead of leaving it to guesswork, which matters because every accepted variant also raises the false-trigger rate. It takes the recordings that were supposed to trigger and didn't, collects what the model actually heard on them, and proposes the candidates within an edit distance of the wake word - measured with the spaces removed, so a word the recognizer split in two scores zero and is recognisable as both the commonest miss and the safest variant. Candidates that also appear on `_silence_` recordings are listed but deliberately not recommended and kept out of the paste-ready config line, because accepting those buys hits at the price of the bot talking over people. Both the resolution rule and the suggestion logic are pure functions, so the ranking and the distance arithmetic are tested rather than trusted.
- A voice per radio (`Radios[].Voice`, empty = the global `VoiceName`): the AWACS, the tanker and the tower can now sound like three people instead of one bot on three frequencies. The voice is resolved once at startup alongside the radio's wake word and callsign, travels with the radio that answers (so it covers tactical replies, ATIS, fixed phrases and the standby acknowledgement alike), and is named in the startup log - a voice name the machine doesn't have fails *silently*, with no audio and no error, so the log line is the only warning there is.
- **List available voices** on CH2 and CH3 (`TtsVoices` in `Darkstar.Core`): reads the voices straight out of `DCS-SR-ExternalAudio.exe` instead of leaving them to be typed from memory, shows them as chips and offers them as autocomplete in every voice field. Deliberately an autocomplete rather than a dropdown, because with Azure or Google configured the valid names are the provider's and a picker would make exactly the best-sounding option impossible to enter. Two things about this were worth documenting rather than discovering twice: the tool prints its voice list from its *argument-error* handler rather than a dedicated switch, so the list is obtained with `--help` and a non-zero exit code is the normal case; and it speaks through SAPI5, so Windows 11's modern "natural" voices are usually invisible to it - which is why the list is shorter than the Windows settings suggest, and why the panel says so instead of letting that read as a bug. The parser is pure and tested against the tool's exact output format, including the voice names that contain a comma of their own.
- Documented that Azure AI Speech and Google Cloud TTS already work through `ExternalAudioExtraArgs` (`--azureCredentials="KEY;region"` / `--googleCredentials="path"`) with the provider's voice name per radio, as do `--gender` and `--culture` when a kind of voice is a safer ask than a specific name.
- Housekeeping for the bot's own folders (`FileRetention` in `Darkstar.Core`): `recordings\` and `logs\` are pruned at startup and once an hour, by age first (`RecordingRetentionDays` 7, `LogRetentionDays` 30) and then by size (`RecordingRetentionMaxMb` 500, `LogRetentionMaxMb` 200), oldest first, with `0` switching either rule off. Recordings run at roughly 100 KB per second of speech and a log file is written per start, so both grew without limit on a server that is simply left running - the previous answer was a sentence in the manual warning about it. The three newest log files are never deleted whatever the limits say, so a 1 MB budget entered by mistake cannot delete the file being written to. Only `*.wav` and `*.log` in those two folders are ever considered; `Backup\` and `grpc-dumps\` are left alone on purpose. Each pass logs what it removed and why. The decision is a pure function of the file list, so the arithmetic is tested with numbers instead of by filling a disk.
- **Alpha check**: "Overlord, Punch 1-1, alpha check bullseye" answers the pilot's *own* position - bearing, range and altitude from their coalition's bullseye - which is how a pilot confirms their navigation still agrees with everybody else's. It is answered before the contact query, so it still works when the sensor source is unusable, which is exactly when a pilot most wants to know whether the bot has them on scope. A caller who cannot be matched to a unit gets `DcsIntelNoPositionReply` rather than a position from nowhere. Triggers in `DcsIntelAlphaCheckTriggers`, classified before the other tactical requests since its phrases share no words with them.
- **Radio check**: "Overlord, radio check" → "Loud and clear." Answered on *every* radio, above the per-radio role gating - a tower, an AWACS and a tanker all answer a radio check, and refusing one because that frequency is "only for airfield requests" would be absurd. It needs no mission data at all, which is the point: when you are trying to find out whether anything works, this is the one call that always answers. With DCS-gRPC on it adds whether the bot has the caller on scope ("Loud and clear, contact." / "…but no radar contact on you."), which is the quickest way to discover that an SRS name and a DCS name don't line up - the failure that otherwise silently turns every BRAA call into a bullseye call. A failed or slow lookup answers the plain version rather than claiming no contact, and the lookup is one unit query with no contact or declination call behind it. A `radio check` row in `phrases.json` still takes priority, so an upgrade never changes wording somebody chose themselves; the default `phrases.json` no longer creates that row.

### Changed
- Only what the bot actually needs on the target machine goes into the installer now. `Setup.iss` packs `publish\bot\*` and `publish\gui\*` wholesale, so anything a NuGet package drops in there gets installed on somebody's PC. `SatelliteResourceLanguages = en` in both app projects drops the localized resource DLLs that the gRPC, protobuf and Blazor WebView packages ship in a subfolder per language - everything this bot says is English, radio phraseology isn't translatable - and `AllowedReferenceRelatedFileExtensions = .pdb` drops the XML API documentation copied next to each referenced assembly, which is for writing code against a library rather than running one. The `.pdb` symbols are deliberately kept: a Windows Service leaves no trace except its log file, and without them the stack traces in that log lose their line numbers. After publishing, `build-installer.ps1` now inventories both folders, prints file count and size, and warns (without failing the build) about any file type a running bot has no use for or any localized folder that survived - so a package finding a third way to smuggle something in gets noticed at build time instead of on a user's disk. `-Clean` also removes the three projects' `obj\` and `bin\` folders, so it is a build from scratch rather than a fresh copy of a stale one.
- Performance and stability pass over the audio and networking paths, measured rather than guessed:
  - **Verbose logging no longer runs when nobody is reading it.** `Debug()` used to write to the log file regardless of `DebugLogging`, and the UDP receive path logs two or three lines per 20 ms packet - measured at ~123 MB of string garbage per hour per talking pilot, plus the same again written to disk. The hot call sites now test `Logger.IsDebugEnabled` before building anything, and verbose lines are only recorded when asked for. Nothing is lost where it counts: the last 200 verbose lines are kept in a ring buffer and written to the file automatically whenever an error is logged, so a failure still arrives with its run-up - handed over once, not repeated for every follow-up error.
  - **The anti-alias filter stopped allocating on every frame.** Two arrays per 20 ms frame per radio came to ~15 MB of garbage per minute; the scratch buffer is now reused. Measured: 275 ms -> 145 ms and 15.1 MB -> 1.9 MB per minute of audio, with the bit-exact frame-boundary tests unchanged.
  - **One Opus decoder per sender instead of one for everyone.** An Opus decoder carries the previous frame's state for prediction and packet-loss concealment, so pushing two pilots' packets through a single shared instance decoded each against the other's history. Decoders are now kept per client GUID, capped at 64 and cleared wholesale if that is ever reached, and guarded by a lock so a future concurrent caller cannot corrupt native state.
  - **gRPC channels are shared per address** (`DcsGrpcChannels`) instead of a fresh HTTP/2 connection per request. A channel owns its connection and is designed to be reused; the previous code paid for a new TCP connection and TLS handshake on every bogey dope, every ATIS call and every threat circle sweep, and left each one in TIME_WAIT. Closed cleanly on shutdown. The explorer and the connection test keep their own short-lived channels on purpose, so a user poking at a wrong address cannot poison the shared one.
  - **The audio event handler can no longer take the process down.** It is attached to an `Action`, so an async lambda on it is `async void` - deliberately, because the UDP read loop must not wait for a Gemini round trip - but that also means an exception escaping it is unhandled. The body is now fully wrapped: a failure costs one transmission and a log line.
  - **Deliberately left alone:** the pre-roll `List<byte>` with `RemoveRange`. It looks like an obvious ring-buffer candidate, but measured it costs 13 ms per minute of audio per radio, and a straightforward ring buffer came out *slower* (35 ms) because `List.RemoveRange` block-copies while a per-byte ring does not. Noted here so the next person doesn't spend an afternoon making it worse.
- Documentation reorganised around the manuals: `docs/manual-en.md` and `docs/manual-de.md` (renamed from `handbuch-de.md`) are the single place where everything is explained, and both README pages were cut down to what belongs on a landing page - features, requirements, project structure and links into the manual.
- Installation is documented as "download the Setup.exe from the Releases page" first; building the installer and running from source are now clearly marked as the developer paths.
- Documentation moved into `docs/` (`manual-en.md`, `manual-de.md`, `configuration.md`, `gui.md`, `contributing.md`, `changelog.md`, `building-the-installer.md`), with `README.md` and the new `README.de.md` acting as short overview pages that link into the full documentation in either language.
- The installer build now always publishes in Release and wipes the publish folders first, so Debug or stale output can never end up in a Setup.exe.
- Removed the unused speech stubs (`StubSpeechToText`, `StubTextToSpeech`, `EchoResponseGenerator`) and the `ITextToSpeech` interface from `SpeechServices.cs` - leftovers from the initial scaffold; reply audio goes through `DCS-SR-ExternalAudio.exe`, not through a .NET interface.
- Project and Windows Service renamed from `DcsSrsHotwordBot` to `Darkstar` / "D.A.R.K.S.T.A.R." throughout the codebase, project files, and installer.
- All source code, comments, and log/console strings translated from mixed German/English to English-only.
- Gemini model updated across two deprecation cycles, settling on `gemini-3.5-flash-lite` for its higher free-tier quota.

### Fixed
- One tower per airfield, generated from the running mission (`TowerPlan` in `Darkstar.Core`, with a button on CH2): reads the airfield list and adds a radio per airfield — callsign `<airfield> Tower`, airfield requests on, tactical off — keeping whatever is already configured and skipping its frequencies rather than reusing them, since two radios on one frequency means the second silently replaces the first. Deterministic by airfield name, so regenerating does not move numbers pilots have written down, and capped at 20 because SRS has its own view on how many radios a client may register.
  - The frequencies are **invented**, because DCS-gRPC does not expose an airfield's radio frequency: the `Airbase` message carries a name, a callsign, a coalition and a position and nothing else, and the real values never leave the mission file. Not much of a loss, since the bot transmits over SRS rather than DCS's own ATIS and needs its own plan — but it does mean the numbers exist nowhere a pilot can look, which is what makes the announcement below load-bearing rather than decorative.
  - The generated towers keep the **global wake word** instead of answering to their airfield's name. "Kobuleti" or "Senaki-Kolkhi" through a small English model, from a non-native speaker, is exactly the failure the position-based airfield lookup was built to avoid — and as a wake word a miss means the bot never reacts at all, with nothing in the log. The frequency identifies the airfield; a test asserts that `Keyword` stays empty.
- A second CH2 button that removes the generated towers again, because generating is additive and a map change would otherwise leave the old map's towers registered alongside the new ones. They are recognised by the whole fingerprint — callsign ending in the configured suffix, airfield requests only, no own wake word — never by a single trait, so a deliberately configured tower that also answers tactical requests stays. With an empty callsign suffix the button finds nothing and says why: there is no fingerprint left, and deleting somebody's configuration on a hunch is worse than making them do it by hand. A hand-built radio matching all four traits is genuinely indistinguishable and goes with them, which is why the button states what it will remove and nothing is written until Save changes.
- Frequencies announced in game (`FrequencyAnnouncer`, on by default): one read-only F10 marker per airfield naming its tower, the radios that are not tied to an airfield, and the wake word — plus one on-screen message at startup for whoever is already flying, which lists the former in full and summarises the towers rather than scrolling a dozen off the screen. Marker ids are deterministic rather than allocated and the whole range is cleared first, so a bot restarted three times in an evening replaces its markers instead of leaving three overlapping sets per airfield, and a smaller mission leaves no orphans. Runs after the SRS connection (announcing frequencies the bot then fails to monitor would be worse than silence) and off the startup path, since an F10 marker is not worth delaying the first transmission for.
- Two test failures that only happened on a German Windows — `got "133,000", expected "133.000"` — and the real problem behind them. A plain `ToString("0.000")` follows whoever is running it, so a frequency came out with a comma on a machine with German regional settings. The pilot-facing formatting was already invariant where it mattered most (F10 markers, spoken frequencies, the altimeter setting), but `TowerPlan`'s notes — shown in the editor next to the frequency fields and copied into radio entries from there — were not, and neither were the log lines. Both applications now set `CultureInfo.InvariantCulture` at startup, which covers every log line and diagnostic without auditing forty interpolations, and the strings a pilot reads or hears state it explicitly so they hold wherever the library is hosted. **The test suite now runs under `de-DE` on purpose**: that is what turns "format numbers invariantly" from a rule somebody has to remember into something that fails immediately, here, instead of on somebody else's server. It found the `TowerPlan` notes within a minute of being switched on.
- Visual Studio refusing to load all three projects, introduced by the version properties added in the same session: the explanatory comment above them mentioned `--version`, and **XML forbids the string `--` inside a comment**. MSBuild on the command line accepted it - the installer built, the test suite stayed green - while Visual Studio's project system rejected the file outright. The suite now parses every `.csproj`, `.xaml` and `.config` in the tree with a real XML reader, which reports it as "An XML comment cannot contain '--'" and names the line. That hole existed because the offline build harness compiles the *sources* through stand-in project files: the repository's own project files were never read by anything that ran.
- A pilot handout, in `docs/kneeboard/`: three pages telling a player what to say, in which words, what it does and what the answer sounds like — rendered as 1536 × 2048 PNGs that drop straight into `Saved Games\DCS\Kneeboard\`, plus a PDF to print or post in Discord. Written for somebody flying rather than somebody configuring, so it also covers what "standby" means, how to read aspect, why the SRS name decides whether BRAA works, and what to do when nothing comes back. The frequency box is deliberately blank and the page says why: those numbers are per server, and a printed one that does not match the SRS is worse than a gap. `build-kneeboard.py` regenerates everything from the HTML source and **fails when a page overflows** — a kneeboard page does not scroll, it just loses its bottom, which is exactly what the first draft did with two of the calls. It also measures how much of the window the browser actually gives the page instead of assuming, after the first renders came out with a grey band where the footer should have been. The suite checks that every call has a spoken wording on it and that the pages are the right size.
- A reference list of every call the bot answers out of the box, in both manuals (chapter 7, "All default calls at a glance"): the mission-data calls, the airfield calls, the radio check and the sample phrases a first start writes, each with what comes back, what it needs, and every default trigger phrase. It also names the one overlap that looks like a bug — `request weather` contains `weather`, an ATIS trigger, and mission-data calls are decided before `phrases.json`, so with the airfield replies on that call gives the real ATIS. The sample phrases moved into `PhraseBook.DefaultPhrases()` so there is a single list to check against, and a test compares all 47 shipped phrases against the list in both manuals — a trigger added to `AppConfig` is otherwise live immediately and documented nowhere a pilot would look.
- **The installer could contain older code than the tree it was built from** — reported twice, and the cause is a property of MSBuild rather than of this script: it decides whether to recompile by comparing timestamps, so a source file dated *earlier* than the previous build's output counts as already built. Unpack an archive over a working copy and that is every file in it. `dotnet publish` then reports success, skips the compile and copies the previous assemblies. Reproduced in four lines (edit a file, backdate it, publish — the old code is still in the output) and fixed three ways: `obj\` and `bin\` of every project are deleted before publishing so no timestamp decides anything; every build gets a unique `InformationalVersion` of `<version>+build.<UTC timestamp>`, which is itself a reason to recompile; and that stamp is **read back out of the published assembly**, with the build stopping and naming both values when it does not match. `--no-incremental` was tried first and is not a valid `dotnet publish` switch — it would have been a silent no-op.
- Which build is this? Nothing used to say: every assembly reported 1.0.0.0 because no version was ever set, which is why "it looks like an older version" could neither be confirmed nor ruled out. `VersionInfo` in `Darkstar.Core` now reports the version and build time the installer stamped in; the bot writes it as the first line of every log and answers `--version` without starting anything, and the config editor shows it in its title bar. A build that did not come from the script reports `0.0.0-dev` and the bot's log says so — normal from source, worth a second look on a server.
- A failure guard in `build-installer.ps1` that could never fire, found while testing the above: an external command's output goes into the enclosing **function's return value**, so `$botOk` was an array of dotnet's console lines and `-not $botOk` was never true. Every check after the publish — exit code, missing executable — was dead. The output now goes through `Out-Host`, which prints the same text and leaves the return value a boolean.
- `build-installer.ps1` ending in the Inno Setup compiler instead of in an installer. Inno Setup does not warn about a `Source:` line matching nothing — it stops with an error — so a Vosk model download that failed four steps earlier (a warning that scrolls past behind a proxy or on a slow link) finished the build with `No files found matching "vosk-model\*"` and nothing in `installer\output`. Reproduced end to end with a stand-in `dotnet` and `ISCC.exe` against a synthetic repository: the old script failed exactly that way, the new one builds the **slim** installer instead, names it `-slim.exe`, and says so in the warnings and the summary — a slim installer that exists beats a full one that doesn't. The same check covers a half-extracted model folder (files but no `am\` and `conf\`) and an empty publish folder, which now reports itself rather than surfacing as a missing wildcard three steps from the cause. Inno Setup itself is also found properly now: its own uninstall registry entry first (which is where a per-user winget installation lives, and the fixed paths missed those entirely), then both `Program Files` folders, `%LOCALAPPDATA%\Programs` and the `PATH`, each matched as `Inno Setup*` so a future version still counts.
- Installer payload reduced to what is needed to run: the `.pdb` debug symbols and the XML documentation are excluded (`Excludes: "*.pdb,*.xml"`), which also stops a release carrying the absolute build path a `.pdb` records. The trade is stated rather than hidden — without symbols a stack trace in the service's log loses its line numbers — and `-WithSymbols` puts them back for a bug being chased on the target machine.
- The installer asks where to install, and knows where it already is. The destination page used to be hidden whenever a previous installation was found (Inno Setup's `auto` default), which is exactly the moment somebody wants to see the path; it is now always shown, prefilled from the existing installation and with a line saying one was found. Two independent sources, because they fail in different situations: the uninstall entry's `InstallLocation`, and the path the Windows Service is registered to run — on a server the service is often all that is left. A recorded path that no longer exists is ignored rather than offered. The point is the mistake it prevents: a second copy in a new folder while the service keeps running the old one.
- Thirteen settings that existed only in `config.json`, found by comparing `AppConfig` against every binding in the editor rather than by reading the panels. The worst of them was a **whole feature with no controls at all**: the frequency announcer (`AnnounceFrequenciesEnabled`, `…Markers`, `…Message`, `…MessageSeconds`) was described in three documents, is on by default, and is the only way pilots ever learn the generated tower frequencies — and the tower card told the operator to leave it on "(CH8)", a channel it had never been on. It now has its own card under the tower generator, with the two halves separately switchable, a warning when DCS-gRPC is off, and the self-referential cross-reference gone. Also added: `WrongChannelReply` with the rule that makes it safe (used only when exactly one other radio serves the request), `UnintelligibleReply` beside the fallback it is not, `PlayerNameCallsignSeparator`, `TowerPlanModulation`, the bullseye triggers next to the bogey dope ones with a hint saying they modify a request rather than being one, and the four threat-circle replies. A test now asserts that **every** `AppConfig` and `RadioConfig` property is bound somewhere in the editor and that no panel sends the operator to the channel they are already on - the documentation tests could not have caught either, since being written down and being reachable are different things.
- Documentation completed where it had quietly fallen behind the code, found by inventorying the sources rather than by rereading the text. Four gaps, each now also held open by a test: **every log tag is explained** — eleven of the twenty-four (`[SRS]`, `[SRS UDP]`, `[Watchdog]`, `[Ack]`, `[Rate limit]`, `[Radio]`, `[Coalition Check]`, `[Gemini]`, `[Discord]`, `[Phrase Match]`, `[Error]`) appeared nowhere, which matters because the log is this project's support channel; chapter 10 now has a table of all of them plus what happens when the SRS connection drops (retry every 5s forever, one Discord message per outage rather than per retry, and why a reconnect causes no burst of tune-in greetings). **Chapter 7 covers every request a pilot can make** — "where is Springfield 2-1?", the standby acknowledgement and the rate limit existed only as settings-table rows, which is where nobody looks to find out what to say. **The installer's setup types are described**, above all `Bot only (headless server)`: on a DCS server it installs nothing with a window and skips the WebView2 runtime entirely, which was discoverable only by running the installer. And the **Discord panel promised three messages where the bot sends five** — a failed start and an unexpected stop were missing from the panel, the GUI documentation and both manuals, which are precisely the two a server nobody is watching needs.
- Config editor navigation grouped rather than listed. The sidebar was nine channels in the order the features had been built, which is why Discord sat between the log and the mission data; it is now four groups — SERVER (CH1, CH9), RADIO & SPEECH (CH2–CH5), MISSION DATA — CH8, MONITORING (CH6, CH7) — with the channel numbers deliberately unchanged, since around ninety places in the documentation say "on CH2 Radios" and a renumbering would silently invalidate all of them. **CH8 is now three entries instead of one**: it had grown into a thousand-line page holding the connection, every tactical and airfield reply setting, two test buttons and a 38-query explorer, and grouping the sidebar does nothing for a page nobody can find anything on. The split is by constant (`DcsGrpcPanel.SectionServer`/`SectionReplies`/`SectionExplorer`), not by string, and the suite checks that the declared sections, the blocks rendering them and the sidebar entries are the same three, plus that no markup sits outside a section — that one would show the same card on all three pages, and a brace closed a line early is exactly how it happens. An entry whose feature is switched off is marked `off`, which says "you turned this off" and never "this is unreachable". The sidebar's vertical rhythm was tightened until all four groups and eleven entries fit above the fold at the window's 600px minimum height, checked by rendering the real stylesheet rather than by eye. Two pieces of panel text were wrong rather than merely stale: CH8 still opened with "not used by replies yet" from before tactical replies existed, and two notices pointed "above" at a toggle that is now on another page.
- Greeting a pilot who tunes in (`TuneInGreeting` in `Darkstar.Core`; `TuneInGreetingEnabled`, off by default, `TuneInGreetingText`, `TuneInGreetingGapSeconds`): when somebody dials in one of the bot's frequencies, it names the channel they reached and where the tactical radio is — the one thing an F10 marker at the departure field cannot tell them once they are airborne, and the generated tower frequencies exist nowhere else. No new data source was needed: every SRS client reports its tuned radios in the sync and in each radio update, and the bot was receiving that and discarding it (a player's tuned frequency is client-side and is exposed neither in the DCS scripting environment nor in DCS-gRPC, so SRS is the only place it exists). Off by default and throttled hard, because SRS has no unicast and the greeting is therefore heard by everybody on the frequency: once per client per frequency for the whole session, a minimum gap per frequency so a flight of four checking in together hears one, the already-greeted check *before* the gap so a repeat tune-in cannot push it out for the next arrival, and transmission through the same path as a reply so it queues instead of talking over the radio. A radio slot SRS marks disabled - and the 1 Hz placeholder frequency that comes with it - is not a tuning; only a changed frequency set counts as an arrival, since SRS also sends radio updates for volume and encryption; the bot's own client is filtered out before any of it, and the opposing coalition is not greeted. Clients are forgotten on disconnect so a server running for weeks does not grow forever, and `{tactical}` never names the channel the pilot is already listening on.
- `.gitignore` rewritten around what must never be committed rather than around build clutter, and `recordings\` was missing from it — the folder `SaveRecordings` fills with one WAV per transmission, holding the recorded **voices of other players** with their SRS names in the file names. That is other people's personal data, and a commit is permanent. The file now leads with the runtime data (`config.json` with the API keys, `recordings\`, `logs\`, `Backup\`, `grpc-dumps\`, `models\`), each entry saying what it holds and why it matters, and adds the editor and profiler state that embeds absolute build paths — which is how a Windows user name reaches a public repository (`*.pubxml`, `.history\`, `_ReSharper*\`, `*.rsuser`, `.idea\`, and others). It also records what a `.gitignore` cannot do: the author name and e-mail in every commit, which is the actual identity leak and needs a noreply address instead. A pointless negation for a bootstrapper that nothing commits and the build downloads itself was dropped. Verified by initialising a throwaway repository: all 85 tracked files still come through, and every one of the private artefacts is refused. The test suite now asserts the coverage, so a future output folder cannot quietly slip past.
- Twelve absolute paths left behind in the test suite by moving it into the repository: those lines read source files from the machine the suites were written on, so they threw on every other one. They now go through `Test.ReadSource("relative/path")`, and `Program.cs` checks for a rooted path literal in the suite's own sources *before* running anything - reporting the file and line rather than failing mid-run with a stack trace where an explanation belongs.
- The bot failing to build as soon as `Darkstar.Tests` existed. `Darkstar.csproj` sits in the repository root, so every other project lives underneath it and the SDK's default glob compiled them all into the bot - producing `Duplicate 'System.Reflection.AssemblyTitleAttribute' attribute` (from the other projects' generated `obj\` files) and `Only one compilation unit can have top-level statements` (two `Program.cs` files), neither of which points anywhere near the cause. The old exclusion was one `<Compile Remove>` per sibling project, a list that had to be extended by hand every time a project was added; it is now a single `<Compile Remove="*\**\*.cs" />`, which is exactly right because all of the bot's own sources sit directly in the root. `build-installer.ps1 -Clean` had the same stale-list problem and now discovers the project folders instead. The test suite checks the property generally rather than this one case: any project with another project beneath it must exclude subfolder sources, and the bot must still keep its own sources in the root, since that is what makes the blanket exclusion safe.
- Bearings of due north spoken as "zero zero zero", which is not something a controller says and reads to a pilot as though the bot had lost the track. All bearing output now goes through `BearingForSpeech`/`BearingText`, which map a bearing into 1-360 - so north is "three six zero" - in the tactical replies, the alpha check and the ATIS wind alike. Calm wind is still reported as calm, not as a direction.
- The log file appearing to fill up only once the bot was stopped. Two independent causes, both about Windows not updating a file's directory entry while a handle is open on it. First, `StreamWriter.AutoFlush` pushes data into the OS cache but never calls `FlushFileBuffers`, so the file's reported size and modification time stayed stale - Explorer showed 0 bytes and everything landed at once when the handle finally closed. The log is now forced all the way to disk, throttled to about once a second so a debug-level flood doesn't mean a disk round trip per UDP packet, and `Logger.Shutdown()` closes it properly instead of leaving that to process exit (which also means a crash no longer loses the lines explaining it). Second, and worse: the config editor's log tail picked "the newest log" by `LastWriteTimeUtc`, which for the same reason ranked the *previous* run's finished log above the one being written - so CH7 showed a stale file until the bot stopped. Log files are now chosen by the timestamp in their name (`LogFiles.PickNewest`), which is accurate the moment the file exists, with hand-renamed files ranked below properly named ones so they can never outrank the live log. The log file is also opened with `FileShare.ReadWrite | FileShare.Delete` so ordinary tail tools can attach to it, and CH7 gained a live view that re-reads every two seconds plus a field naming the file it is showing.
- The bot answering "bogey dope" whenever it could not make out a transmission. Two things combined: `"Bogey Dope"` was one of the default terms in `vocabulary.json`, and the transcription prompt instructs Gemini to transcribe anything that merely *sounds like* a vocabulary term as that term - so unintelligible audio was snapped onto the one command-shaped phrase in the list. The naive `Contains` check in the classifier then fired, and tactical requests are answered before phrases and Gemini, so the invented request won. Fixed at every step: the trigger phrase is out of the default vocabulary; the bot warns at startup (and the config editor marks the chips in red) when any vocabulary term is also a trigger phrase, which catches it in configurations that already exist on disk; trigger phrases are now matched as whole phrases with word boundaries (`TriggerMatcher`) instead of as bare substrings, in both the tactical and the airfield classifier; a transmission that yields no transcript is answered with a configurable repeat request (`UnintelligibleReply`) and never reaches the classifiers at all; and the log now names the trigger that fired next to the transcript it fired on, so the next occurrence explains itself.
- The bot dying with `System.AccessViolationException` in `Vosk.VoskPINVOKE.new_VoskRecognizer` when the Vosk model was missing: Vosk's native loader returns a null pointer for a bad model path, the C# wrapper stores it without complaint, and the process was then torn down inside the first recognizer - as a fatal error .NET cannot catch, so nothing could report it. The model folder is now checked before the native call (`VoskModelCheck` in `Darkstar.Core`: folder exists, holds `am\final.mdl` or `conf\model.conf`), the loaded model is verified to have a native handle before anything is built from it, and a missing `libvosk.dll` is reported as a missing Visual C++ Redistributable. A model unpacked one folder too deep is found and used, with a note saying so. A configured-but-unusable model stops the bot with an explanation rather than falling back to the volume detector, which would have looked like a working bot that answers every loud noise.
- Wrong default for `ExternalAudioExePath`: it pointed at `DCS-SimpleRadio-Standalone\Server\DCS-SR-ExternalAudio.exe`, but SRS ships the tool in its `ExternalAudio` subfolder. New installs got a path that doesn't exist, which only surfaced as silent replies. The default is corrected, and the detection above means it is normally overwritten with the real path anyway.
- Installer registering the Windows Service with an unquoted executable path: with the default install location under `C:\Program Files\...`, the space in the path meant Windows could fail to start the registered service. The path is now quoted inside the service's `ImagePath`.
- Second (and further) configured radios ignoring their own wake word and only responding to the first/default radio's hotword: `SrsConnection` always routed incoming audio using `packet.Frequencies[0]`, which does not reliably correspond to the radio actually transmitted on. Audio is now matched against every configured radio's frequency (rounded to the nearest Hz) and dispatched to the correct `RadioSession` accordingly, with a same-as-before fallback to the first frequency only when none match a monitored radio at all.
- Hotword cross-triggering between radio channels (a radio reacting to another radio's keyword) after the routing fix above: `VoskHotwordDetector` compared the configured keyword against recognized text with a plain substring `Contains()` check, including against Vosk's *partial* (unstable, in-progress) results - a weaker/smaller Vosk model can transiently mis-transcribe audio into text that happens to contain another radio's keyword as a substring. Matching is now done with a whole-word, case-insensitive regex (`\bKEYWORD\b`) instead, so a keyword only matches as a standalone word. This reduces false positives but does not eliminate them if the recognition model itself is too weak; using a larger Vosk model (`-VoskModelSize Standard` or `Large` in `setup-dev-environment.ps1`) remains the recommended fix for persistent recognition-quality issues.
- Self-inflicted PTT "heartbeat click" artifact, caused by UDP keepalive pings carrying a non-empty frequency array; fixed by sending keepalives with an empty frequency array so the server has nothing to relay.
- Audio feedback loop where the bot would hear and respond to its own transmitted reply; fixed with a self-mute flag that suppresses hotword processing during the bot's own reply transmission.
- Recording never finalizing when the far end stops transmitting without trailing silence packets; fixed with a watchdog timeout that finalizes the recording based on time-since-last-packet rather than relying solely on silence-frame counting.
- Potential silent data loss from an invalid/corrupted `config.json` being silently replaced with a blank default; `AppConfig.LoadOrCreateDefault` now detects JSON parse errors explicitly and refuses to overwrite the file.

### Removed
