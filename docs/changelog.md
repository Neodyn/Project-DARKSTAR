# Changelog

All notable changes to this project are documented here. Format loosely follows [Keep a Changelog](https://keepachangelog.com/); this project doesn't yet use formal version tags, so entries are grouped by feature area in the order they were introduced.

## [Unreleased]

### Added
- Config file (`config.json`) auto-created with default values on first run; the bot exits after creating it so values can be reviewed before starting.
- Google Gemini integration for combined speech-to-text and reply generation in a single API call (conserves free-tier quota), with configurable retry/backoff (`GeminiMaxRetries`, `GeminiRetryDelayMs`) and an optional fallback model (`GeminiFallbackModel`).
- Vosk offline wake-word detection (no cloud account needed) as the sole hotword engine.
- Fixed-phrase system (`phrases.json`): known question/answer pairs answered directly, with a configurable fallback response and a `RestrictToKnownPhrases` toggle.
- Vocabulary hints (`vocabulary.json`) passed to Gemini to improve transcription accuracy for non-standard-English terms.
- Compact, leveled, colored console logging with full detail always written to timestamped files under `logs/`, plus a global `LoggingEnabled` kill switch and a `DebugLogging` verbosity toggle.
- Config and phrase file syntax/value validation, with warnings written to the log rather than blocking startup.
- Automatic schema-merge: new config fields introduced by an update are added to existing `config.json` files with default values, without touching existing settings.
- Automatic timestamped backups of `config.json`/`phrases.json`/`vocabulary.json` to a `Backup/` subfolder before any automatic edit.
- Windows Service hosting support, using the same executable as the console app (via Generic Host / `Microsoft.Extensions.Hosting.WindowsServices`).
- Optional Discord webhook notifications for bot start/stop and SRS connection loss/recovery, gated behind a `DiscordEnabled` flag (default `false`) so the integration is entirely opt-in.
- Multi-radio support (`Radios` list): multiple frequencies monitored simultaneously, each with independent hotword detection, recording state, and reply channel.
- Coalition awareness: requester's coalition is looked up from the SRS client list; `RestrictToOwnCoalition` can make the bot ignore requests from the opposing coalition entirely.
- Per-radio custom wake word and callsign (`Radios[].Keyword` / `Radios[].Callsign`), falling back to the global `VoskKeyword`/`BotCallsign` when unset.
- Blazor Hybrid (WPF + WebView2) GUI configuration editor (`Darkstar.Gui`) covering Connection, Radios, Speech, Phrases, Vocabulary, Discord, and Logging settings, sharing `Darkstar.Core` with the bot service so both always read/write the same config files.
- Automatic shared-config-folder detection so the GUI and the bot service resolve to the same `config.json`/`phrases.json`/`vocabulary.json` by default.
- Player-name callsign parsing: pilots named `CALLSIGN 1-1 | PlayerName` in DCS are addressed as `CALLSIGN 1-1` in replies, with the separator configurable via `PlayerNameCallsignSeparator`.
- TTS-friendly callsign pronunciation: hyphens in spoken callsigns are replaced with spaces so "1-1" is read as "one one" rather than being misread as "eleven" or spoken with an audible pause.
- Inno Setup Windows installer bundling the bot, the GUI, and a Vosk model, with optional Windows Service registration and automatic `VoskModelPath` configuration.
- Installer now also installs every runtime dependency the bot and GUI need on a bare Windows machine: the .NET 8 Desktop Runtime (covering both components), the Visual C++ Redistributable (needed by Vosk's native `libvosk.dll`), and the WebView2 Runtime (needed by the GUI) — each skip-if-already-installed. Both projects switched from self-contained to framework-dependent publishing accordingly, keeping the installer smaller.
- DCS-gRPC groundwork: NuGet bindings (`RurouniJones.Dcs.Grpc`), a `DcsGrpcTester` connectivity check, and a GUI test panel, as the foundation for future real mission-data features (bogey dope, picture, bullseye calls).
- Slim installer variant: `build-installer.ps1 -Slim` (alias of `-SkipVoskModel`) passes `/DNoVoskModel` to Inno Setup, which drops the speech model, its component and the pre-filled `VoskModelPath` from the installer - a few MB instead of up to ~2 GB - and names the result `DARKSTAR-Setup-<version>-slim.exe` so both variants can sit side by side.
- `build-installer.ps1`: builds the whole distributable installer with one command - checks the build machine's prerequisites (.NET 8 SDK, Inno Setup, offering a winget install for the latter), publishes bot and GUI, downloads the three dependency installers and a Vosk model of the chosen size, and compiles `installer\Setup.iss`. Re-runnable, with `-DryRun`, `-Clean`, `-SkipVoskModel`, `-SkipDependencyDownload` and a `-Version` that is now passed through into the installer and its file name.
- Selectable contact source for the tactical replies (`DcsIntelContactSource`): `AwacsThenMissionData` (the previous behaviour), `AwacsOnly` - god's eye switched off entirely, so an empty detection table is honestly reported as a clean picture - or `MissionDataOnly`. In `AwacsOnly`, a failed sensor call or a missing unit name answers "no tactical data" instead of implying an empty sky, and a threat circle skips that sweep rather than suggesting the airspace is clear.
- Threat circle: a pilot can arm a standing watch by radio ("Overlord, threat circle forty miles") and the bot then keeps checking a circle of that radius around the pilot's own aircraft - it moves with them - warning them on the same frequency as soon as a hostile aircraft or helicopter enters it. The radius is understood as digits or words; each contact is announced once per circle; warnings are capped per sweep so a whole package can't monopolize the frequency, and they hold briefly while the pilot is transmitting. A circle ends by voice command, after a configurable time limit, or when the pilot leaves the mission.
- Clearer speech pacing for tactical replies (`DcsIntelSlowSpeech`, on by default): bearings get a comma between their digits so TTS pauses briefly instead of running "zeroninerzero" together, and ranges, altitudes and counts are spelled out as words ("thirty five miles" rather than a rattled-off "35").
- Aircraft/helicopter type announcement in tactical replies is now on by default (`DcsIntelSayContactType`), covers picture and threat calls as well as bogey dope, strips DCS variant suffixes before speaking (`F-16C_50` → `F-16C`), and reports a group flying several types as "mixed, lead &lt;type&gt;".
- `ExternalAudioExtraArgs`: free-form extra command-line arguments appended to every `DCS-SR-ExternalAudio.exe` call, for options that depend on the installed SRS version (such as a speaking-rate flag).
- **Windows Service management in the GUI** (new CH9 panel, backed by `WindowsServiceManager` in `Darkstar.Core`): install the bot as a service with optional delayed auto-start, start/stop it, and remove it again.
  - Removal stops the service and waits for it to actually reach "Stopped" before deleting, so no ghost entry is left behind.
  - Shows the live state and the executable the service is really registered to run, and detects an installation made under the installer's service name.
  - Asks for elevation per operation (UAC) instead of requiring the editor itself to run as administrator.
  - Implemented via PowerShell rather than by parsing `sc.exe` output, which is localized and unparseable on non-English Windows.
- **Tactical replies from live mission data** (`DcsIntelService` in `Darkstar.Core`, configured on the GUI's DCS-gRPC panel): the bot answers "bogey dope", "picture" and "threat check" from the running mission instead of from `phrases.json`/Gemini.
  - Contacts come from the sensors of a configured AWACS unit (`ControllerService.GetDetectedTargets`), falling back to plain mission data when no unit is configured, the unit is player-flown (DCS only fills AI detection tables), or the call fails.
  - Bearings are magnetic and read digit by digit for TTS.
  - Bogey dope gives BRAA with aspect (hot/flanking/beaming/cold) from the requesting pilot's own aircraft — located by matching their SRS name against the DCS player names — and falls back to the bullseye format when that pilot can't be identified.
  - Includes range/group limits, configurable trigger phrases, and a GUI test button that shows the exact reply without transmitting.
- Optional "message received, standby" acknowledgement (`AckEnabled` / `AckAfterSeconds` / `AckMessage`, editable in the GUI's Speech panel): if transcription and reply generation take longer than the configured number of seconds — counted from the wake word — the bot transmits a short holding message so the pilot knows the call was picked up. Sent per radio with that radio's own callsign, supports `{pilot}` / `{callsign}` placeholders, is skipped entirely when the real reply is ready in time, and never talks over a pilot who is still transmitting (transmissions per radio are serialized).
- DCS-gRPC mission data explorer in the GUI (CH8, backed by `DcsGrpcExplorer` in `Darkstar.Core`): a strictly read-only browser for what a running mission exposes - 38 queries across mission, time, world, coalition, players/server, group/unit, environment and live event/unit streams, shown as raw JSON. Includes a one-click mission snapshot, autocomplete of unit/group names discovered in earlier results, "take position from unit" for weather/declination queries, time-limited live stream recording, and copy/save-to-file (`grpc-dumps/`).
- **SRS installation detection** (`SrsPaths` in `Darkstar.Core`): the installer seeds `ExternalAudioExePath` in the initial `config.json` with this machine's real `DCS-SR-ExternalAudio.exe`.
  - Found via SRS's own uninstall entry in the registry or, failing that, by probing the known install layouts under both `Program Files` folders, per-user locations and every fixed drive.
  - The config editor's CH1 Connection panel gained a **Detect SRS installation** button that does the same at runtime, and resolves a folder typed into the field to the executable inside it.
  - Startup validation now names the path it found when the configured one doesn't exist.
  - The installer's `WriteInitialConfig` runs for every variant, so the slim installer seeds the SRS path too.
- **Installer upgrades an existing installation in place.** A stable `AppId` plus the version written to (and read back from) the uninstall registry entry let it tell an update from a reinstall from a downgrade.
  - Reuses the previous install folder and component/task choices, states on the "Ready to Install" page which of the three it is, and asks for confirmation before installing an older version over a newer one.
  - The Windows Service is stopped in `PrepareToInstall` and started again afterwards — without that the update fails on a locked `Darkstar.exe`, since a running service holds its own executable open.
  - A service registration pointing at an old path is removed and recreated rather than left stale, and `CloseApplications` handles a config editor that happens to be open.
  - `build-installer.ps1 -Version` validates the version and derives the four-part `VersionInfoVersion` for the Setup.exe's file properties.
- Readable startup failures instead of runtime crash dumps: `BotService.ExecuteAsync` wraps the whole startup, logs what went wrong as a sentence with concrete next steps, and stops the host with a meaningful exit code (2 = configuration, 3 = unexpected); `Program.cs` additionally logs unhandled and unobserved-task exceptions to the log file, which is the only place a Windows Service leaves any trace at all.
- **Proper anti-alias filtering** before the 48 kHz → 16 kHz reduction that feeds Vosk (`AudioFrontEnd` in `Darkstar.Core`) — the audio path wake-word detection depends on. Selectable via `HotwordAudioFilter` (`LowPass` default, `Average` for comparison) on CH3 Speech.
  - The previous code averaged three neighbouring samples and dropped two, leaving content above 8 kHz only 5–22 dB down as it folded back into the speech range — 10 kHz landing on 6 kHz, 12 kHz on 4 kHz, right where consonants are told apart.
  - A 161-tap windowed-sinc low-pass puts those fold-over products 60–79 dB down instead (measured against test tones, not estimated).
  - The filter carries its delay line across the 20 ms frame boundaries, which the old stateless version could not, and no longer loses up to two samples per frame on chunk lengths that aren't a multiple of three.
- `Darkstar.exe --test-hotword <file-or-folder>`: runs recorded audio through the real detector in the same 20 ms frames the live path uses and reports hits, misses and what Vosk actually transcribed. `--compare` runs both audio paths side by side and says which did better on that material; `--keyword`/`--model`/`--filter` try alternatives without touching `config.json`. Connects to nothing, so it is safe to run while the service is live.
- `SaveRecordings`: writes every transmission to `recordings\` as a WAV tagged `_hit_` or `_missed_` — including the transmissions where the wake word did *not* fire, which previously left no trace anywhere and are exactly the cases worth studying. Together with `--test-hotword` this turns "did that change help?" into a number. Off by default.
- `HotwordAutoGain`: optional evening-out of how loud different pilots arrive, deliberately timid (amplify only, capped at +16 dB, never adapting on near-silence) and off by default, because an eager automatic gain lifts noise into speech range and invents wake words. Never affects the audio that is transcribed or saved.
- `WavUtils.ReadPcm16` / `ToMono`: WAV reading that walks the chunk list instead of assuming a 44-byte header, so recordings made in Audacity or by SRS itself can be fed to `--test-hotword`; non-PCM and non-16-bit files are refused with a message that says why.
- `AppConfig.LoadReadOnly`: reads config.json without creating it, merging fields, logging or backing anything up, for tools that only want to look at the settings.
- **Tolerant pilot-name matching** (`PilotNames` in `Darkstar.Core`), which decides whether a tactical reply can use BRAA from the pilot's own aircraft or has to fall back to bullseye.
  - The SRS player name and the DCS player name are typed in different places and rarely agree character for character. The previous exact comparison failed on all of the usual differences: squadron tags (`[ISAF] Mobius 1-1`), flight numbers written `11` instead of `1-1`, and different spacing or capitalisation.
  - Names are now reduced to a canonical key, with the rules tried strictest first (exact, then canonical full name / handle / callsign, then a narrow unique-substring rule) and each applied across all units before the next, so a weak rule can never beat a strong one.
  - The substring rule deliberately ignores the unit's callsign field, because that holds the *flight's* callsign shared by every aircraft in it — matching partially there would hand a wingman's BRAA call to the flight lead, which a test now guards against.
  - Ambiguity is refused rather than guessed, and whichever rule matched (or why none did) is written to the log, since the bullseye fallback is silent on the radio and previously left no trace.
- Squadron tags are stripped from spoken callsigns, and flight numbers are spoken digit by digit: "Spare 15" is read as "Spare one five" rather than "Spare fifteen", and `[ISAF] Mobius 1` no longer has its brackets read out. Threat circles are keyed by the canonical name too, so a pilot who rejoins with their tag written differently can still cancel the circle they set up.
- **"Runway in use" and ATIS answered from the running mission** (`DcsAirfieldService` in `Darkstar.Core`, off by default via `DcsAirfieldEnabled`): live wind, temperature and pressure from `AtmosphereService`, and the runway end with the most headwind.
  - A pilot can name the airfield or leave it out, in which case the one nearest their aircraft is used.
  - Designators are the magnetic heading rounded to ten (0 becoming 36), preferring DCS's own name for the strip when it agrees to within one so the call matches the kneeboard, `L`/`R` included.
  - Exact ties are broken by the smaller crosswind and then the longer runway, so the answer doesn't depend on the order DCS listed the strips in.
  - Units are converted from what DCS actually hands over — Kelvin, Pascals, metres per second, radians — and the altimeter setting is read in hectopascals, inches or both (`DcsAirfieldPressureUnit`).
- Runway headings are read through `CustomService.Eval`, because DCS-gRPC's `Airbase` message carries no runway data and `Airbase.getRunways()` is reachable no other way. Since `Eval` runs arbitrary Lua, the snippet is a compile-time constant that asks for *all* airfields at once so no name has to be interpolated, it only reads, and it runs once per DCS session; tests assert those properties. `Eval` is disabled on DCS-gRPC servers by default, so a refusal is reported once with the exact setting to change (`evalEnabled = true`) and the weather part keeps working with the runway reported as unknown.
- `DcsIntelService.SpeakDigit`: one shared digit vocabulary for every number read digit by digit, so the aviation "niner" that bearings already used now applies to wind, pressure and temperature as well. Temperature is read digit by digit ("temperature one five") rather than as a word ("fifteen"), which is how an ATIS sounds.
- **The airfield a request is about is decided by the pilot's own position first**, and only then by a name in the transcript.
  - Airfield names are the weakest link in the feature: "Mineralnye Vody", "Kobuleti" and "Batumi" are exactly what speech recognition gets wrong, and a mis-transcription that happened to match a different airfield produced a confidently wrong answer.
  - Within `DcsAirfieldAtFieldNm` (5 NM) of a field the position wins outright, so *"Overlord, active runway for Punch 1-1"* works from the ramp with no airfield spoken at all. Deliberately naming a different field still works, and the log notes the discrepancy.
  - Beyond `DcsAirfieldMaxDistanceNm` (60 NM) with nothing named, the bot asks instead of reporting a field hundreds of miles away as though the pilot were there.
  - Every reply names the airfield it used, and the log says how it was chosen.
- **A pilot saying their own callsign now identifies them** (`PilotNames.FindMatchInTranscript`) — a second, independent route when their SRS name and their DCS name don't line up, which is the usual reason a BRAA call silently becomes a bullseye call.
  - Spoken digits are converted back to figures first (`NormalizeSpokenNumbers`, including "niner"/"tree"/"fife"), so "for Punch one one" and "for Punch 1-1" both reach the unit DCS calls `Punch 1-1`.
  - Keys must be at least five characters and match exactly one pilot, so two pilots named in one transmission is refused rather than guessed at.
  - The tactical replies use the same lookup, and an airfield name that only matches because it is part of the requesting pilot's own callsign is no longer read as naming an airfield.
- **Per-radio roles**, so the bot's jobs can be split across frequencies the way a real radio plan does — the AWACS on one, the tower on another.
  - `Radios[].AnswerTacticalRequests` and `Radios[].AnswerAirfieldRequests` are three-way: `null` follows the global switch, which is what every existing configuration keeps doing; `true`/`false` decide for that radio alone.
  - The global switches remain the master, so a radio can narrow what the bot does but never widen it.
  - The startup log states each radio's job, the config editor shows three Default/On/Off buttons per radio with the resulting role spelled out underneath, and validation warns when a globally enabled feature is switched off on every radio.
- A request that lands on the wrong frequency is handed off rather than refused: "Contact Overlord on two five one decimal zero" (`WrongChannelReply`, with `{callsign}` and `{frequency}` placeholders; the frequency is read digit by digit). Only when exactly one other radio serves the request - with two towers configured there is no single right answer, so none is given and the transmission falls through to `phrases.json` as before.
- `setup-dev-environment.ps1`: a PowerShell script that checks/installs the .NET 8 SDK, required Visual Studio workloads, the WebView2 Runtime, and a Vosk model, then does a trial restore/build — including a project-structure check that catches misplaced `.csproj` files before Visual Studio does.
- **The test suite is in the repository.** `Darkstar.Tests` is a fourth project in the solution: 682 assertions, one command (`dotnet run --project Darkstar.Tests`), a readable transcript and exit code 0 when everything held.
  - It needs no SRS server, no DCS, no Gemini key and no speech model — a test that only runs with a mission loaded is a test nobody runs.
  - Until now these lived outside the repository, which meant nobody but their author could run them or check the numbers they produced; that was the largest single gap in the project.
  - No test framework on purpose: the assertions are about spoken sentences, arithmetic and whether the code still matches its own comments, none of which needs xUnit, and a dependency-free test project still builds in five years.
  - `Darkstar.Core` grants it `InternalsVisibleTo`, so the helpers under test stay `internal` rather than being made public purely to be reachable.
- GitHub Actions (`.github/workflows/build.yml`): builds the solution in Release and runs the suite on every push and pull request, on `windows-latest` because `Darkstar.Gui` is WPF and a green tick on Linux would never have covered it. A second job publishes the bot exactly as the installer does and fails if the output contains anything but the file types a running bot needs - which catches a NuGet package quietly dropping localized resource folders or XML documentation into what gets installed on somebody's machine.
- `WavUtils` moved from the bot into `Darkstar.Core`. It is pure PCM/WAV format handling with no console, audio-device or UI dependency, which is what this project means by shared - and the tests build the WAV files they feed through the audio path from it.
- **Rate limiting per pilot** (`RateLimiter` in `Darkstar.Core`; `RateLimitMaxRequests` 6, `RateLimitWindowSeconds` 120, `RateLimitReply`).
  - Every transmission costs a Gemini call and occupies the frequency while the reply is spoken. One pilot repeating the wake word — bored, annoyed at being misheard, or with a stuck transmit key feeding cockpit noise — could exhaust the quota for everybody and block the channel at the same time, and neither failure looked like the pilot who caused it.
  - Checked after the coalition check and before the Gemini call, so the request is refused before it costs anything.
  - A **sliding window** rather than a cooldown, so a pilot asking three things in quick succession and then flying for ten minutes is never held up.
  - **Refused transmissions are not counted**, because counting them would move the window forward on every retry, and a limit that turns into a ban is not what was configured.
  - The refusal is **spoken once and then silent**, because repeating it would occupy exactly the frequency being protected. Both cases are logged, so a pilot complaining they were ignored leaves a trace.
  - Pilots with no recent traffic are forgotten from the watchdog loop.
- Documentation checks in the test suite, because documentation drifts silently: a setting added to `AppConfig` works perfectly and is simply never written down, and nothing notices for months. The suite now reflects over `AppConfig` and `RadioConfig` and fails when any of the 106 settings is missing from `manual-en.md`, `manual-de.md` or `configuration.md`; it does the same for the nine `--test-hotword` options, for the source-file map in `contributing.md`, and for every internal cross-reference across all nine documents. That last one immediately found a dead link: a reference to the German chapter 8.4 used the English heading's slug, which looks right and never resolves.
- `contributing.md` gained a real source-file map - one line per file across the bot and `Darkstar.Core`, which had grown to 39 files while the document still named a handful - plus the conventions that are not obvious from reading the code: trigger phrases go through `TriggerMatcher`, no trigger phrase belongs in the default vocabulary, nothing user-supplied is interpolated into the runway Lua, decision logic goes in a pure function so it can be tested at all, and a capability that reveals information needs a reason to be on.
- Filled the remaining documentation gaps the new checks turned up: `DcsAirfieldUnknownReply` and `DcsAirfieldUnavailableReply` were only in `configuration.md`, the `--autogain` and `--variants` options were in neither manual, the channel overviews in chapter 6 still described the editor from several features ago, and chapter 8.3 did not mention that switching the tactical replies on is also what brings in the alpha check and the friendly-position card.
- Friendly positions: "Overlord, Punch 1-1, where is Springfield 2-1?" answers where another human player on the caller's own side is, as a BRAA from the caller's aircraft or from the bullseye when that can't be found, with the friendly's own heading because where they are is only half of a rejoin. Aspect is deliberately never given - it describes a contact closing on you, which is meaningless about a wingman. **Off by default**, and assignable per radio as a third role alongside tactical and airfield, because a bot that reads out any player's position on request changes how a PvP server plays and that is the owner's decision rather than a default to hand them.
  - The target is found by POSITION in the sentence rather than by scanning it for names. Such a request names two pilots, and `PilotNames` refuses to choose when more than one is named - the safeguard that caught a wingman being reported as their flight lead. Rather than loosening it, `TriggerMatcher.FindMatchWithTail` returns what follows the trigger and only that is searched, which has exactly one answer. The cost is that the name must come after the phrase; pronouns are recognised as naming nobody, so "where is he?" asks which aircraft instead of reporting no contact on "he".
  - Human players only (`CoalitionService.GetPlayerUnits`). AI units are never pulled in: a candidate list of every AI on the coalition makes misidentification likely, and on this particular request that means confidently telling somebody the wrong position.
  - A caller whose coalition is unknown is refused outright, before any player is looked up. Everywhere else an unknown sender coalition falls back to the bot's own side, which is harmless when the answer concerns the enemy - here it would let somebody in a spectator slot ask where the bot's side is.
  - Answered before the hostile contact query, like the alpha check, so it still works when the sensor source is unusable. A caller asking about themselves gets an alpha check rather than "bearing 000, 0 miles".
- **Wake-word variants**, for crews that are not native English speakers (`VoskKeywordVariants`, `Radios[].KeywordVariants`, and `HotwordVariants` in `Darkstar.Core`).
  - The hotword runs through a small English model, so on a German-speaking server "Overlord" arrives as "over lord", "oberlord" or worse — and the first of those already failed the `\bOverlord\b` match on the space alone, so the bot stayed silent with nothing anywhere to say why.
  - A radio now accepts a set of spellings rather than one, still matched as whole words, with runs of whitespace inside a variant matching any whitespace.
  - **Variants follow the word, not the radio:** a radio using the global wake word inherits the global variants, a radio with its own `Keyword` starts from an empty list — otherwise a tanker on "Texaco" would quietly begin answering to a variant meant for the AWACS.
  - The startup log names every accepted spelling, since they are the one thing that can make a radio react to something that is not its wake word.
  - This is not model training, which would be a Kaldi run with hours of labelled audio; it accepts what the existing model already produces.
- **`Darkstar.exe --test-hotword recordings --suggest-variants`**: works the variant list out of real recordings instead of leaving it to guesswork, which matters because every accepted variant also raises the false-trigger rate.
  - It takes the recordings that were supposed to trigger and didn't, collects what the model actually heard on them, and proposes the candidates within an edit distance of the wake word.
  - Distance is measured with the spaces removed, so a word the recognizer split in two scores zero — recognisable as both the commonest miss and the safest variant.
  - Candidates that also appear on `_silence_` recordings are listed but deliberately not recommended, and kept out of the paste-ready config line, because accepting those buys hits at the price of the bot talking over people.
  - Both the resolution rule and the suggestion logic are pure functions, so the ranking and the distance arithmetic are tested rather than trusted.
- A voice per radio (`Radios[].Voice`, empty = the global `VoiceName`): the AWACS, the tanker and the tower can now sound like three people instead of one bot on three frequencies. The voice is resolved once at startup alongside the radio's wake word and callsign, travels with the radio that answers (so it covers tactical replies, ATIS, fixed phrases and the standby acknowledgement alike), and is named in the startup log - a voice name the machine doesn't have fails *silently*, with no audio and no error, so the log line is the only warning there is.
- **List available voices** on CH2 and CH3 (`TtsVoices` in `Darkstar.Core`): reads the voices straight out of `DCS-SR-ExternalAudio.exe` instead of leaving them to be typed from memory, shows them as chips and offers them as autocomplete in every voice field.
  - Deliberately an autocomplete rather than a dropdown: with Azure or Google configured the valid names are the provider's, and a picker would make exactly the best-sounding option impossible to enter.
  - The tool prints its voice list from its *argument-error* handler rather than a dedicated switch, so the list is obtained with `--help` and a non-zero exit code is the normal case.
  - It speaks through SAPI5, so Windows 11's modern "natural" voices are usually invisible to it — which is why the list is shorter than the Windows settings suggest, and why the panel says so instead of letting that read as a bug.
  - The parser is pure and tested against the tool's exact output format, including the voice names that contain a comma of their own.
- Documented that Azure AI Speech and Google Cloud TTS already work through `ExternalAudioExtraArgs` (`--azureCredentials="KEY;region"` / `--googleCredentials="path"`) with the provider's voice name per radio, as do `--gender` and `--culture` when a kind of voice is a safer ask than a specific name.
- **Housekeeping for the bot's own folders** (`FileRetention` in `Darkstar.Core`): `recordings\` and `logs\` are pruned at startup and once an hour, by age first (`RecordingRetentionDays` 7, `LogRetentionDays` 30) and then by size (`RecordingRetentionMaxMb` 500, `LogRetentionMaxMb` 200), oldest first, with `0` switching either rule off.
  - Recordings run at roughly 100 KB per second of speech and a log file is written per start, so both grew without limit on a server that is simply left running — the previous answer was a sentence in the manual warning about it.
  - The three newest log files are never deleted whatever the limits say, so a 1 MB budget entered by mistake cannot delete the file being written to.
  - Only `*.wav` and `*.log` in those two folders are ever considered; `Backup\` and `grpc-dumps\` are left alone on purpose.
  - Each pass logs what it removed and why. The decision is a pure function of the file list, so the arithmetic is tested with numbers instead of by filling a disk.
- **Alpha check**: "Overlord, Punch 1-1, alpha check bullseye" answers the pilot's *own* position - bearing, range and altitude from their coalition's bullseye - which is how a pilot confirms their navigation still agrees with everybody else's. It is answered before the contact query, so it still works when the sensor source is unusable, which is exactly when a pilot most wants to know whether the bot has them on scope. A caller who cannot be matched to a unit gets `DcsIntelNoPositionReply` rather than a position from nowhere. Triggers in `DcsIntelAlphaCheckTriggers`, classified before the other tactical requests since its phrases share no words with them.
- **Radio check**: "Overlord, radio check" → "Loud and clear."
  - Answered on *every* radio, above the per-radio role gating — a tower, an AWACS and a tanker all answer a radio check, and refusing one because that frequency is "only for airfield requests" would be absurd.
  - It needs no mission data at all, which is the point: when you are trying to find out whether anything works, this is the one call that always answers.
  - With DCS-gRPC on it adds whether the bot has the caller on scope ("Loud and clear, contact." / "…but no radar contact on you.") — the quickest way to discover that an SRS name and a DCS name don't line up, the failure that otherwise silently turns every BRAA call into a bullseye call.
  - A failed or slow lookup answers the plain version rather than claiming no contact, and the lookup is one unit query with no contact or declination call behind it.
  - A `radio check` row in `phrases.json` still takes priority, so an upgrade never changes wording somebody chose themselves; the default `phrases.json` no longer creates that row.

- **Four controller calls adopted from the brevity a real GCI uses**, all on CH8 → Replies, all also in the manuals and the kneeboard.
  - **`declare`** — *"declare bullseye zero three zero for four five"* answers **hostile**, **friendly**, **furball** or **clean** for what sits within 5 NM of that point. Say "bullseye" and the point is measured from the bullseye; leave the word out and it is measured from the caller's own aircraft, which is a completely different place.
  - **Furball is reported first and never as "hostile".** It needs our own side as well as the enemy's, which is a second contact query with the other coalition. If that query cannot be read — an `AwacsOnly` source has no detection table for friendlies — the reply says *"unable to check friendlies"* rather than making a claim the bot is not in a position to make.
  - **`spike`** — *"spike two seven zero"* names the nearest contact within 15° either side of that bearing, and says **buddy spike** when the nearest thing out there is one of ours. A warning receiver gives a rough direction, not a precise one, which is what the cone is for. Nothing known on that bearing is answered as *"clean on bearing …, no contact known"* — not the same claim as "nothing is there".
  - **Neither is bounded by `DcsIntelMaxRangeNm`.** The pilot named the place, so both answer before the range filter and before the "picture clean" shortcut: a declare at bullseye 030 for 45 can be a hundred miles away, and a buddy spike with no hostiles anywhere is still something the pilot needs to hear.
  - **`divert`** — *"vector to nearest"* gives bearing, range and field elevation to the nearest airfields, two by default. Answered before the weather query, so it still works when the conditions are the thing that is broken. **No TACAN channel and no tower frequency**: DCS-gRPC exposes neither, and a made-up one sends a pilot who is already in trouble to tune a dead radio.
  - **Picture formations and fill-ins.** Two groups are called *azimuth* or *range*, three a *wall*, *ladder*, *vic* or *champagne*, and each group now carries *single* / *two contacts* / *heavy*, then *fast*, then the type — a controller's order, not alphabetical. Measured from the pilot's own aircraft, because from the bullseye the same three groups make a different shape.
  - Tanking and the landing grade were deliberately left out.
- **`check in`, `check out` and `say again`.** Three calls about the pilot rather than the enemy, answered before the mission data is consulted at all — somebody asking for a repeat usually does so because something else is already broken.
  - **`say again` repeats any reply**, not only a tactical one: the calls most often missed are the long ones and the longest is the ATIS. On every radio, with no DCS connection needed. Asking twice gives the same answer twice, and the repeat carries no *"I say again"* preamble in front of a long ATIS.
  - **`check out` also ends that pilot's threat circle** on that radio, rather than leaving a watch sweeping for an aircraft whose pilot has said goodbye.
  - **`DcsIntelCheckInGatesCalls`** (default `false`) limits the bot's one unprompted transmission — the threat circle warning — to pilots who checked in. Off by default because a pilot who never learns the phrase would otherwise lose a warning they used to get, and lose it silently. **Asking for a threat circle counts as checking in**, so a request can never be accepted and then ignored.
  - `say again` and `check in` were default rows in `phrases.json` answering with canned sentences, which is what those rows were for before the bot could do the real thing. They are gone from the defaults; an existing row still wins, exactly as the radio check's does.
  - At most 200 pilots are kept on file, oldest first out. A dedicated server cycles through names for weeks.

- **The bot keeps score of its own listening.** A line every twenty-five transmissions and the full picture at shutdown: how many were understood as a call, how many matched nothing, how many were a pilot simply saying it again. Nothing to switch on.
  - **One figure is not the bot's own opinion of how it did.** A pilot keying up again within twenty seconds of something that was *not* answered as a call is the pilot saying the answer was no good. A high repeat count next to a healthy percentage means the bot is confidently answering the wrong thing — a different fault from not hearing at all, and one no self-assessment would ever report.
  - **The report ends with the words the transcriber really produced**, commonest first, for the calls that matched nothing. Those spellings go straight into a trigger list or into `KeywordVariants`; until now somebody had to notice them going past in the log.
  - Percentages start at ten transmissions, because one understood call out of one is not a hundred percent of anything. The last 2,000 are kept, so a server running for days reports a window rather than leaking memory.
  - The running line exists because a dedicated server is usually killed rather than stopped, and a report that only appears at shutdown is one nobody sees.

### Changed
- **Every setting is now proven to survive a save** (`SavingTests`). "I changed it, saved, and nothing happened" has three possible causes and only one of them is the bot; this covers the middle one. All 136 settings are given a value that is not their default by reflection, written, read back and compared — including the nested per-radio ones — so a new setting is covered the day it is added rather than when somebody remembers to extend a list. The editor's own bindings are checked too: every comma-separated trigger field writes back into the config, and every binding to a local field is one of the ten transient ones named in the test, so a new local field holding a real setting fails the check instead of being silently dropped on save.
- **Every `config.json` validation warning now carries the file's full path** instead of the bare name `config.json`, for the reason above: the bare name is the one thing that cannot say *which copy*, and it is read as naming the file the operator just edited.
- **Only what the bot actually needs on the target machine goes into the installer.** `Setup.iss` packs `publish\bot\*` and `publish\gui\*` wholesale, so anything a NuGet package drops in there gets installed on somebody's PC.
  - `SatelliteResourceLanguages = en` in both app projects drops the localized resource DLLs that the gRPC, protobuf and Blazor WebView packages ship in a subfolder per language — everything this bot says is English, and radio phraseology isn't translatable.
  - `AllowedReferenceRelatedFileExtensions = .pdb` drops the XML API documentation copied next to each referenced assembly, which is for writing code against a library rather than running one.
  - The `.pdb` symbols are deliberately kept: a Windows Service leaves no trace except its log file, and without them the stack traces in that log lose their line numbers.
  - After publishing, `build-installer.ps1` inventories both folders, prints file count and size, and warns (without failing the build) about any file type a running bot has no use for or any localized folder that survived — so a package finding a third way to smuggle something in gets noticed at build time instead of on a user's disk.
  - `-Clean` also removes the three projects' `obj\` and `bin\` folders, so it is a build from scratch rather than a fresh copy of a stale one.
- Performance and stability pass over the audio and networking paths, measured rather than guessed:
  - **Verbose logging no longer runs when nobody is reading it.** `Debug()` used to write to the log file regardless of `DebugLogging`, and the UDP receive path logs two or three lines per 20 ms packet - measured at ~123 MB of string garbage per hour per talking pilot, plus the same again written to disk. The hot call sites now test `Logger.IsDebugEnabled` before building anything, and verbose lines are only recorded when asked for. Nothing is lost where it counts: the last 200 verbose lines are kept in a ring buffer and written to the file automatically whenever an error is logged, so a failure still arrives with its run-up - handed over once, not repeated for every follow-up error.
  - **The anti-alias filter stopped allocating on every frame.** Two arrays per 20 ms frame per radio came to ~15 MB of garbage per minute; the scratch buffer is now reused. Measured: 275 ms -> 145 ms and 15.1 MB -> 1.9 MB per minute of audio, with the bit-exact frame-boundary tests unchanged.
  - **One Opus decoder per sender instead of one for everyone.** An Opus decoder carries the previous frame's state for prediction and packet-loss concealment, so pushing two pilots' packets through a single shared instance decoded each against the other's history. Decoders are now kept per client GUID, capped at 64 and cleared wholesale if that is ever reached, and guarded by a lock so a future concurrent caller cannot corrupt native state.
  - **gRPC channels are shared per address** (`DcsGrpcChannels`) instead of a fresh HTTP/2 connection per request. A channel owns its connection and is designed to be reused; the previous code paid for a new TCP connection and TLS handshake on every bogey dope, every ATIS call and every threat circle sweep, and left each one in TIME_WAIT. Closed cleanly on shutdown. The explorer and the connection test keep their own short-lived channels on purpose, so a user poking at a wrong address cannot poison the shared one.
  - **The audio event handler can no longer take the process down.** It is attached to an `Action`, so an async lambda on it is `async void` - deliberately, because the UDP read loop must not wait for a Gemini round trip - but that also means an exception escaping it is unhandled. The body is now fully wrapped: a failure costs one transmission and a log line.
  - **Deliberately left alone:** the pre-roll `List<byte>` with `RemoveRange`. It looks like an obvious ring-buffer candidate, but measured it costs 13 ms per minute of audio per radio, and a straightforward ring buffer came out *slower* (35 ms) because `List.RemoveRange` block-copies while a per-byte ring does not. Noted here so the next person doesn't spend an afternoon making it worse.

- **Documentation completed where it had quietly fallen behind the code**, found by inventorying the sources rather than by rereading the text. Four gaps, each now also held open by a test:
  - **Every log tag is explained.** Eleven of the twenty-four (`[SRS]`, `[SRS UDP]`, `[Watchdog]`, `[Ack]`, `[Rate limit]`, `[Radio]`, `[Coalition Check]`, `[Gemini]`, `[Discord]`, `[Phrase Match]`, `[Error]`) appeared nowhere, which matters because the log is this project's support channel. Chapter 10 now has a table of all of them, plus what happens when the SRS connection drops: retry every 5 s forever, one Discord message per outage rather than per retry, and why a reconnect causes no burst of tune-in greetings.
  - **Chapter 7 covers every request a pilot can make.** "Where is Springfield 2-1?", the standby acknowledgement and the rate limit existed only as settings-table rows, which is where nobody looks to find out what to say.
  - **The installer's setup types are described**, above all `Bot only (headless server)`: on a DCS server it installs nothing with a window and skips the WebView2 runtime entirely, which was discoverable only by running the installer.
  - **The Discord panel promised three messages where the bot sends five.** A failed start and an unexpected stop were missing from the panel, the GUI documentation and both manuals — precisely the two a server nobody is watching needs.
- **Config editor navigation grouped rather than listed.** The sidebar was nine channels in the order the features had been built, which is why Discord sat between the log and the mission data.
  - It is now four groups — SERVER (CH1, CH9), RADIO & SPEECH (CH2–CH5), MISSION DATA (CH8), MONITORING (CH6, CH7) — with the channel numbers deliberately unchanged, since around ninety places in the documentation say "on CH2 Radios" and a renumbering would silently invalidate all of them.
  - **CH8 is now three entries instead of one.** It had grown into a thousand-line page holding the connection, every tactical and airfield reply setting, two test buttons and a 38-query explorer, and grouping the sidebar does nothing for a page nobody can find anything on.
  - The split is by constant (`DcsGrpcPanel.SectionServer`/`SectionReplies`/`SectionExplorer`), not by string, and the suite checks that the declared sections, the blocks rendering them and the sidebar entries are the same three — plus that no markup sits outside a section, which would show the same card on all three pages, and a brace closed a line early is exactly how that happens.
  - An entry whose feature is switched off is marked `off`, which says "you turned this off" and never "this is unreachable".
  - The sidebar's vertical rhythm was tightened until all four groups and eleven entries fit above the fold at the window's 600 px minimum height, checked by rendering the real stylesheet rather than by eye.
  - Two pieces of panel text were wrong rather than merely stale: CH8 still opened with "not used by replies yet" from before tactical replies existed, and two notices pointed "above" at a toggle that is now on another page.
- **Greeting a pilot who tunes in** (`TuneInGreeting` in `Darkstar.Core`; `TuneInGreetingEnabled`, off by default, `TuneInGreetingText`, `TuneInGreetingGapSeconds`): when somebody dials in one of the bot's frequencies, it names the channel they reached and where the tactical radio is — the one thing an F10 marker at the departure field cannot tell them once they are airborne, and the generated tower frequencies exist nowhere else.
  - No new data source was needed: every SRS client reports its tuned radios in the sync and in each radio update, and the bot was receiving that and discarding it. A player's tuned frequency is client-side and is exposed neither in the DCS scripting environment nor in DCS-gRPC, so SRS is the only place it exists.
  - Off by default and throttled hard, because SRS has no unicast and the greeting is therefore heard by everybody on the frequency: once per client per frequency for the whole session, and a minimum gap per frequency so a flight of four checking in together hears one.
  - The already-greeted check runs *before* the gap, so a repeat tune-in cannot push it out for the next arrival, and transmission goes through the same path as a reply so it queues instead of talking over the radio.
  - A radio slot SRS marks disabled — and the 1 Hz placeholder frequency that comes with it — is not a tuning. Only a changed frequency set counts as an arrival, since SRS also sends radio updates for volume and encryption.
  - The bot's own client is filtered out before any of it, and the opposing coalition is not greeted.
  - Clients are forgotten on disconnect so a server running for weeks does not grow forever, and `{tactical}` never names the channel the pilot is already listening on.
- **`.gitignore` rewritten around what must never be committed** rather than around build clutter — and `recordings\` was missing from it.
  - That is the folder `SaveRecordings` fills with one WAV per transmission, holding the recorded **voices of other players** with their SRS names in the file names. That is other people's personal data, and a commit is permanent.
  - The file now leads with the runtime data (`config.json` with the API keys, `recordings\`, `logs\`, `Backup\`, `grpc-dumps\`, `models\`), each entry saying what it holds and why it matters.
  - It adds the editor and profiler state that embeds absolute build paths — which is how a Windows user name reaches a public repository (`*.pubxml`, `.history\`, `_ReSharper*\`, `*.rsuser`, `.idea\`, and others).
  - It also records what a `.gitignore` cannot do: the author name and e-mail in every commit, which is the actual identity leak and needs a noreply address instead.
  - A pointless negation for a bootstrapper that nothing commits and the build downloads itself was dropped.
  - Verified by initialising a throwaway repository: all 85 tracked files still come through, and every one of the private artefacts is refused. The test suite now asserts the coverage, so a future output folder cannot quietly slip past.
- Twelve absolute paths left behind in the test suite by moving it into the repository: those lines read source files from the machine the suites were written on, so they threw on every other one. They now go through `Test.ReadSource("relative/path")`, and `Program.cs` checks for a rooted path literal in the suite's own sources *before* running anything - reporting the file and line rather than failing mid-run with a stack trace where an explanation belongs.
- **The bot failing to build as soon as `Darkstar.Tests` existed.** `Darkstar.csproj` sits in the repository root, so every other project lives underneath it and the SDK's default glob compiled them all into the bot.
  - That produced `Duplicate 'System.Reflection.AssemblyTitleAttribute' attribute` (from the other projects' generated `obj\` files) and `Only one compilation unit can have top-level statements` (two `Program.cs` files), neither of which points anywhere near the cause.
  - The old exclusion was one `<Compile Remove>` per sibling project, a list that had to be extended by hand every time a project was added. It is now a single `<Compile Remove="*\**\*.cs" />`, which is exactly right because all of the bot's own sources sit directly in the root.
  - `build-installer.ps1 -Clean` had the same stale-list problem and now discovers the project folders instead.
  - The test suite checks the property generally rather than this one case: any project with another project beneath it must exclude subfolder sources, and the bot must still keep its own sources in the root, since that is what makes the blanket exclusion safe.
- Bearings of due north spoken as "zero zero zero", which is not something a controller says and reads to a pilot as though the bot had lost the track. All bearing output now goes through `BearingForSpeech`/`BearingText`, which map a bearing into 1-360 - so north is "three six zero" - in the tactical replies, the alpha check and the ATIS wind alike. Calm wind is still reported as calm, not as a direction.
- **The log file appearing to fill up only once the bot was stopped.** Two independent causes, both about Windows not updating a file's directory entry while a handle is open on it.
  - `StreamWriter.AutoFlush` pushes data into the OS cache but never calls `FlushFileBuffers`, so the file's reported size and modification time stayed stale — Explorer showed 0 bytes and everything landed at once when the handle finally closed.
  - The log is now forced all the way to disk, throttled to about once a second so a debug-level flood doesn't mean a disk round trip per UDP packet, and `Logger.Shutdown()` closes it properly instead of leaving that to process exit — which also means a crash no longer loses the lines explaining it.
  - Worse, the config editor's log tail picked "the newest log" by `LastWriteTimeUtc`, which for the same reason ranked the *previous* run's finished log above the one being written, so CH7 showed a stale file until the bot stopped.
  - Log files are now chosen by the timestamp in their name (`LogFiles.PickNewest`), which is accurate the moment the file exists, with hand-renamed files ranked below properly named ones so they can never outrank the live log.
  - The log file is also opened with `FileShare.ReadWrite | FileShare.Delete` so ordinary tail tools can attach to it, and CH7 gained a live view that re-reads every two seconds plus a field naming the file it is showing.
- **The bot answering "bogey dope" whenever it could not make out a transmission.** Two things combined: `"Bogey Dope"` was one of the default terms in `vocabulary.json`, and the transcription prompt instructs Gemini to transcribe anything that merely *sounds like* a vocabulary term as that term — so unintelligible audio was snapped onto the one command-shaped phrase in the list. The naive `Contains` check in the classifier then fired, and tactical requests are answered before phrases and Gemini, so the invented request won. Fixed at every step:
  - The trigger phrase is out of the default vocabulary.
  - The bot warns at startup, and the config editor marks the chips in red, when any vocabulary term is also a trigger phrase — which catches it in configurations that already exist on disk.
  - Trigger phrases are now matched as whole phrases with word boundaries (`TriggerMatcher`) instead of as bare substrings, in both the tactical and the airfield classifier.
  - A transmission that yields no transcript is answered with a configurable repeat request (`UnintelligibleReply`) and never reaches the classifiers at all.
  - The log now names the trigger that fired next to the transcript it fired on, so the next occurrence explains itself.
- **The bot dying with `System.AccessViolationException`** in `Vosk.VoskPINVOKE.new_VoskRecognizer` when the Vosk model was missing.
  - Vosk's native loader returns a null pointer for a bad model path, the C# wrapper stores it without complaint, and the process was then torn down inside the first recognizer — as a fatal error .NET cannot catch, so nothing could report it.
  - The model folder is now checked before the native call (`VoskModelCheck` in `Darkstar.Core`: folder exists, holds `am\final.mdl` or `conf\model.conf`), and the loaded model is verified to have a native handle before anything is built from it.
  - A missing `libvosk.dll` is reported as a missing Visual C++ Redistributable, and a model unpacked one folder too deep is found and used, with a note saying so.
  - A configured-but-unusable model stops the bot with an explanation rather than falling back to the volume detector, which would have looked like a working bot that answers every loud noise.
- Wrong default for `ExternalAudioExePath`: it pointed at `DCS-SimpleRadio-Standalone\Server\DCS-SR-ExternalAudio.exe`, but SRS ships the tool in its `ExternalAudio` subfolder. New installs got a path that doesn't exist, which only surfaced as silent replies. The default is corrected, and the detection above means it is normally overwritten with the real path anyway.
- Installer registering the Windows Service with an unquoted executable path: with the default install location under `C:\Program Files\...`, the space in the path meant Windows could fail to start the registered service. The path is now quoted inside the service's `ImagePath`.
- Second (and further) configured radios ignoring their own wake word and only responding to the first/default radio's hotword: `SrsConnection` always routed incoming audio using `packet.Frequencies[0]`, which does not reliably correspond to the radio actually transmitted on. Audio is now matched against every configured radio's frequency (rounded to the nearest Hz) and dispatched to the correct `RadioSession` accordingly, with a same-as-before fallback to the first frequency only when none match a monitored radio at all.
- **Hotword cross-triggering between radio channels** (a radio reacting to another radio's keyword) after the routing fix above.
  - `VoskHotwordDetector` compared the configured keyword against recognized text with a plain substring `Contains()` check, including against Vosk's *partial* (unstable, in-progress) results — and a weaker or smaller Vosk model can transiently mis-transcribe audio into text that happens to contain another radio's keyword as a substring.
  - Matching is now done with a whole-word, case-insensitive regex (`\bKEYWORD\b`), so a keyword only matches as a standalone word.
  - This reduces false positives but does not eliminate them if the recognition model itself is too weak. A larger Vosk model (`-VoskModelSize Standard` or `Large` in `setup-dev-environment.ps1`) remains the recommended fix for persistent recognition-quality issues.
- Self-inflicted PTT "heartbeat click" artifact, caused by UDP keepalive pings carrying a non-empty frequency array; fixed by sending keepalives with an empty frequency array so the server has nothing to relay.
- Audio feedback loop where the bot would hear and respond to its own transmitted reply; fixed with a self-mute flag that suppresses hotword processing during the bot's own reply transmission.
- Recording never finalizing when the far end stops transmitting without trailing silence packets; fixed with a watchdog timeout that finalizes the recording based on time-since-last-packet rather than relying solely on silence-frame counting.
- Potential silent data loss from an invalid/corrupted `config.json` being silently replaced with a blank default; `AppConfig.LoadOrCreateDefault` now detects JSON parse errors explicitly and refuses to overwrite the file.
